# PolisJAPAN アーキテクチャ

システム全体の構成、主な処理の流れ、リポジトリの構成、設計判断の理由をまとめる。各部分の詳細は、節ごとに示す文書を参照。

## 1. 全体構成

常時起動のサーバーを持たない、フルサーバーレスの構成である。画面は静的サイトとして配信し、データは S3 上の CSV をブラウザが直接読む。サーバーの処理は、AI によるテーマ生成、下書きの受け付け、pol.is との同期に限られる。

```
利用者のブラウザ
  │
  ├─ pol-is.jp ─────── CloudFront → S3 ………… LP（静的サイト）
  ├─ app.pol-is.jp ─── CloudFront → S3 ………… WEB アプリ（静的サイト）と CSV（テーマ一覧・集計）
  ├─ pol.is ──────────────────────────── 投票・意見投稿の画面（iframe で埋め込み）
  ├─ api.pol-is.jp ─── API Gateway → Lambda「api」… AI テーマ生成、下書きの投稿、管理 API
  ├─ contact.pol-is.jp ─ CloudFront → API Gateway → Lambda → SES … お問い合わせメール
  └─ share.pol-is.jp ── CloudFront → API Gateway → Lambda … 共有リンク（OGP を含む HTML を返して転送）

運営者のブラウザ
  └─ admin.pol-is.jp ── CloudFront（IP 制限）→ S3 … 管理画面（api.pol-is.jp の管理 API を呼ぶ）

定期実行（EventBridge Scheduler）
  ├─ 5 分ごと  → Lambda「batch-update」… pol.is の集計を取得し、S3 の CSV を更新
  └─ 15 分ごと → Lambda「batch-create」… 承認済みの下書きを 1 件、pol.is に作成して一覧に追加

データ
  ├─ S3 `app.pol-is.jp` の `csv/` ………… テーマ一覧と集計（ブラウザが読む、読み取り専用のデータ）
  ├─ DynamoDB `polisjapan-drafts` ……… テーマの下書き
  └─ SSM Parameter Store ………………… シークレット

監視
  └─ Route53 ヘルスチェック、CloudWatch アラーム → SNS → メール
```

| 構成要素 | 役割 | 詳細 |
| --- | --- | --- |
| LP・WEB アプリ・管理画面 | フレームワークを使わない静的サイト | `docs/クライアント設計.md`、`docs/画面仕様書.md` |
| Lambda「api」 | FastAPI のアプリ。AI テーマ生成、下書きの登録、管理 API | `docs/API仕様.md`、`docs/サーバー設計.md` |
| Lambda「batch-update」 | pol.is から集計を取得して CSV を更新する | `docs/サーバー設計.md` |
| Lambda「batch-create」 | Selenium で pol.is を操作し、テーマを作成する | `docs/サーバー設計.md` |
| CSV・DynamoDB | データの保存 | `docs/データ仕様.md` |
| AWS の各リソース | 配信、API、バッチ、監視の基盤 | `docs/インフラ構成.md` |

## 2. 主な処理の流れ

### 2.1 テーマを見る

1. ブラウザが `app.pol-is.jp` から HTML・JS・CSS を取得する。
2. JS が `csv/themes.csv` を取得し、テーマのカードを描画する。絞り込み、検索、並び替えはすべてブラウザの中で行う。

サーバーの処理は通らない。API が止まっていても、一覧と詳細の表示は動く。

### 2.2 投票する・意見を投稿する

1. 詳細画面が、URL の `conversation_id` を使って pol.is の埋め込みスクリプトを読み込む。
2. 投票と意見の投稿は、埋め込まれた pol.is の画面（iframe）が pol.is と直接やり取りする。

PolisJAPAN のサーバーは投票を受け取らない。投票の内容や投票者の情報も持たない。

### 2.3 集計を反映する

1. 5 分ごとに batch-update が起動し、全テーマの集計 CSV を pol.is から取得する。
2. 投票数か意見数が変わったテーマについて、集計 CSV と `csv/themes.csv` を S3 に書き込む。
3. ブラウザは、詳細画面の分析タブで集計 CSV を読み、グラフを描く。

CSV は 5 分でキャッシュが切れるように配信している。バッチの間隔と合わせると、反映までの遅れは最大で 10 分程度になる。

### 2.4 テーマを作る

1. 利用者が作成画面でテーマを入力する。AI アシストでは、ブラウザが `/theme/generate_axis`、`/theme/generate_comments`、`/theme/generate_descriptions` を順に呼び、Lambda「api」が OpenAI で対立軸・意見・説明を生成する。
2. 投稿すると、ブラウザが `/theme/post_draft` を呼び、下書きが DynamoDB に「承認済み」で登録される。
3. 15 分ごとに batch-create が起動し、承認済みの下書きを古い順に 1 件取り出す。Selenium で pol.is にログインし、カンバセーションを作成して、シード意見を登録する。
4. 成功すると、`csv/themes.csv` に行を足し、下書きを「投稿済み」にする。一覧に新しいテーマが出る。
5. 失敗すると、次回以降の起動で再試行する。同じ下書きが 9 回連続で失敗すると「隔離」にして、次の下書きへ進む。

運営者の審査は挟まない。これは仕様である。

### 2.5 下書きを管理する

1. 運営者が、許可された回線から `admin.pol-is.jp` を開き、アクセスキーを入力する。
2. 管理画面が `/admin/info` で下書きの一覧を取得する。編集は `/admin/edit`、承認（隔離された下書きの再投稿）は `/admin/approve`、削除は `/batch/delete` を呼ぶ。

管理画面と管理 API は、どちらも同じ IP 許可リストを検査する。

### 2.6 問い合わせる・共有する

- **お問い合わせ**: ブラウザが `contact.pol-is.jp` の API に送信し、Lambda が SES で運営と送信者にメールを送る。
- **共有**: 詳細画面が `share.pol-is.jp` のリンクを作る。このリンクを開くと、Lambda がカード表示用の情報（OGP）を含む HTML を返し、ブラウザを詳細画面へ転送する。

### 2.7 監視する・反映する

- **監視**: API の死活、Lambda の実行エラー、投稿の滞留をアラームで検知し、メールで通知する。
- **反映**: `main` ブランチへの push で、GitHub Actions がクライアントとサーバーを自動デプロイする。インフラは Terraform を手動で実行する。

手順は `docs/運用手順書.md`。

## 4. 設計の方針

- **利用者が触れる部分は、マネージドサービスで配信する。** LP、アプリ、CSV は S3 と CloudFront で配信し、アクセスが増えても落ちにくくする。静的な配信なので、改ざんや侵入の余地も小さい。
- **サーバーの処理を最小にする。** 投票は pol.is、一覧と分析はブラウザと CSV で完結させ、サーバーが必要なのは AI 生成と下書きの受け付けだけにする。
- **常時起動のサーバーを持たない。** 固定費と、OS の更新や SSH の管理をなくす。
- **データを守る。** CSV は S3 のバージョニング、下書きは DynamoDB のポイントインタイムリカバリで保護し、どちらも Terraform から削除できないようにしている。
- **インフラはコードで管理する。** 手作業の設定を残さない。

## 5. 設計判断とその理由

| 判断 | 理由 |
| --- | --- |
| 下書きの保存先は DynamoDB の 1 テーブル | 実際に使うテーブルが下書きの 1 つだけで、RDS を置くと固定費がかかるため |
| Lambda はコンテナイメージで配布する | LangChain 系の依存が大きく、zip の上限に収まらないため |
| テーマの作成（Selenium）も Lambda で動かす | 1 テーマの作成が Lambda の上限（15 分）に収まるため。収まらなくなった場合の代替は ECS Fargate のスケジュールタスク |
| batch-create は 1 回の起動で 1 件だけ処理する | 15 分の制限に確実に収め、失敗の影響を 1 件に限るため |
| CSV の更新は CloudFront の無効化ではなく TTL で反映する | 5 分ごとの無効化は無料枠を超えて費用がかかるため |
| 死活監視は Route53 のヘルスチェックで行う | HTTP の応答確認で足り、ブラウザを動かす監視より大幅に安いため。HTTPS で確認するので証明書の失効も検知できる |
| 管理画面の IP 制限は WAF ではなく CloudFront Function で行う | WAF は固定費がかかり、CloudFront Function は実質無料のため。API 側でも同じ許可リストを検査する |
| Provisioned Concurrency を使わない | 初回の応答が数秒遅くなるが、常時の費用をかけない方針のため |
| 投稿の滞留は「件数」で監視する | 失敗した下書きを隔離すると処理が正常終了になり、実行エラーのアラームはすぐ OK に戻る。件数で見ないと滞留に気づけない |
| Chrome のバージョンを固定する | 固定しないと、イメージを作り直すたびに Chrome が上がり、Lambda 上で起動できなくなることがあるため |
| お気に入りは localStorage に保存する | ログイン機能が無く、端末内の保存で足りるため。Cookie は容量が小さく、全リクエストに付いて送られるので使わない |
| お知らせの本文は HTML ファイルで持つ | CSV と Markdown では表現力が足りなかったため |
| ホームの既定の並び順は更新順 | カードに表示する日時と並び順を一致させるため |
| 詳細画面の意見は、グループ横断の合意スコア順に並べる | 利用者の要望「異なるグループ間で賛成の多い意見こそ合意として示すべき」に応えるため。スコアは各グループの平滑化した賛成率 `(賛成+1)/(投票+2)` の積で、投票の無いグループは中立として扱い、票の少ないグループの極端な値を抑える。スコアは並び順にだけ使い、画面には表示しない |
| お問い合わせはアプリ内のモーダルで完結させる | LP のフォームへ移動すると、アプリに戻る導線が切れるため |

運用費は、設計時の見積もりで AWS の合計が月数ドル（OpenAI の利用料は別）。実際の額は AWS の請求で確認する。
