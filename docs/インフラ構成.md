# PolisJAPAN インフラ構成

本番環境の AWS リソースを、配信・API・バッチ・データ・監視・権限・Terraform の順にまとめる。システム全体の構成と処理の流れは [アーキテクチャ.md](アーキテクチャ.md)、デプロイ・障害対応・シークレット変更などの手順は [運用手順書.md](運用手順書.md) を参照。この文書には手順を書かない。

ここに書く設定値は、Terraform（`Infra/terraform/`）の定義と、AWS CLI で確認した実環境の両方に基づく。食い違いが見つかった場合は実環境を正とする。

## 1. 全体像

### 1.1 構成図

```
利用者のブラウザ
  │
  ├─ pol-is.jp ─────────── CloudFront E1L9GH70CTWAY6 ─→ S3 `pol-is.jp`（ウェブサイトエンドポイント）
  ├─ app.pol-is.jp ─────── CloudFront E1VDGUET2Z2OBX ─→ S3 `app.pol-is.jp`（ウェブサイトエンドポイント）
  │                           └─ /csv/* だけ専用キャッシュポリシー（クエリ _v をキーに含める）
  ├─ api.pol-is.jp ─────── API Gateway HTTP API `polisjapan-api`（リージョナル、ap-northeast-3）
  │                           └─ Lambda `polisjapan-api`
  ├─ contact.pol-is.jp ─── CloudFront E2X1TX47YAAO8F ─→ API Gateway REST `PolisJAPAN-Contact`（us-east-1）
  │                           └─ Lambda `PolisJAPAN-Contact` ─→ SES（us-east-1）
  └─ share.pol-is.jp ───── CloudFront E2VD4O5M17XG0X ─→ API Gateway REST `PolisJAPAN-GetOGP`（us-east-1）
                              └─ Lambda `PolisJAPAN-GetOGP`

運営者のブラウザ
  └─ admin.pol-is.jp ───── CloudFront E2D8XIPYTKLR5Z（CloudFront Function で IP 制限）─→ S3 `admin.pol-is.jp`（OAC）

EventBridge Scheduler（ap-northeast-3）
  ├─ rate(5 minutes)  ─→ Lambda `polisjapan-batch-update`
  └─ rate(15 minutes) ─→ Lambda `polisjapan-batch-create`

データ（ap-northeast-3）
  ├─ S3 `app.pol-is.jp` の csv/ ……… テーマ一覧と集計（Lambda が書き、ブラウザが読む）
  ├─ DynamoDB `polisjapan-drafts` …… テーマの下書き
  ├─ S3 `polisjapan-archive` ………… 保全用アーカイブ
  ├─ ECR `polisjapan-api` / `polisjapan-batch-create` … Lambda のコンテナイメージ
  └─ SSM Parameter Store `/polisjapan/*` … シークレット

監視
  ├─ Route53 ヘルスチェック（https://api.pol-is.jp/batch/healthcheck）
  │     └─ CloudWatch アラーム（us-east-1）─→ SNS `polisjapan-alerts`（us-east-1）─→ メール
```

VPC、EC2、RDS、NAT ゲートウェイは使っていない。Lambda はすべて VPC の外で動く。

### 1.2 AWS アカウントとリージョン

AWS アカウントは 1 つ（`133078632695`）で、本番環境だけがある。ステージング環境は無い。主なリージョンは大阪（`ap-northeast-3`）で、次のものだけが `us-east-1` にある。

| us-east-1 にあるもの | 理由 |
| --- | --- |
| CloudFront 用の ACM 証明書（`pol-is.jp`、`app.pol-is.jp`、`admin.pol-is.jp`、`contact.pol-is.jp`、`share.pol-is.jp`） | CloudFront は us-east-1 の証明書しか使えない |
| アラーム `polisjapan-api-healthcheck-failed` と、その通知先の SNS `polisjapan-alerts` | Route53 ヘルスチェックのメトリクスは us-east-1 にしか出ない |
| お問い合わせ・共有の Lambda、API Gateway（REST）、SES | 手動で作られたときからこのリージョンにある |

CloudFront、Route53、IAM はグローバルなサービスである。

同じアカウントには、本システムと関係のないリソース（別ドメインのホストゾーンや SES の ID など）もある。本システムのリソースは、名前が `polisjapan-` / `PolisJAPAN-` で始まるか、`pol-is.jp` に関係する。Terraform が作ったリソースにはタグ `Project = PolisJAPAN`、`ManagedBy = terraform` が付く（`Infra/terraform/environments/production/providers.tf` の `default_tags`）。

## 3. 静的サイトの配信

### 3.1 S3 バケット

| バケット | 役割 | 公開 | 配信方式 | バージョニング | ライフサイクル |
| --- | --- | --- | --- | --- | --- |
| `pol-is.jp` | LP | 公開（バケットポリシーで `s3:GetObject` を全員に許可） | 静的ウェブサイトホスティング（インデックス `index.html`） | 無効 | なし |
| `app.pol-is.jp` | WEB アプリと、`csv/` 配下の本番データ | 公開（同上） | 静的ウェブサイトホスティング（インデックス `index.html`） | 有効 | 古いバージョンを 7 日で削除（ルール名 `BackUp 1-Week`） |
| `admin.pol-is.jp` | 管理画面 | 非公開（ブロックパブリックアクセスをすべて有効） | CloudFront の OAC 経由だけ。バケットポリシーで、ディストリビューション `E2D8XIPYTKLR5Z` からの `s3:GetObject` だけを許可 | 無効 | なし |

どのバケットも大阪にあり、既定の暗号化（SSE-S3、AES256）がかかっている。`pol-is.jp` と `app.pol-is.jp` は、ブロックパブリックアクセスをすべて無効にしている（CloudFront のオリジンが S3 のウェブサイトエンドポイントで、公開読み取りが前提のため）。

`app.pol-is.jp` の `csv/` は、バッチの Lambda が書き込む本番データである。デプロイのワークフローは `csv/*` を同期の対象から外しており、加えてデプロイ用ロールの IAM ポリシーでも `app.pol-is.jp/csv/*` への書き込みと削除を拒否している（§9.1）。誤って上書きした場合は、バージョニングで 7 日以内の版に戻せる。CSV の中身は `docs/データ仕様.md` を参照。

`pol-is.jp` と `app.pol-is.jp` は Terraform の `prevent_destroy` で削除を拒否している。`admin.pol-is.jp` には付けていない（中身はリポジトリから再デプロイできる）。

### 3.2 CloudFront ディストリビューション

5 つのディストリビューションがある。どれも HTTP は HTTPS へリダイレクトし、HTTP/2、TLS は `TLSv1.2_2021` 以上、地域制限なし、アクセスログなし、WAF なしである。

| ID | ドメイン | オリジン | 価格クラス | IPv6 |
| --- | --- | --- | --- | --- |
| `E1L9GH70CTWAY6` | `pol-is.jp` | S3 ウェブサイトエンドポイント `pol-is.jp.s3-website.ap-northeast-3.amazonaws.com`（HTTP） | `PriceClass_All` | 有効 |
| `E1VDGUET2Z2OBX` | `app.pol-is.jp` | S3 ウェブサイトエンドポイント `app.pol-is.jp.s3-website.ap-northeast-3.amazonaws.com`（HTTP） | `PriceClass_All` | 有効 |
| `E2D8XIPYTKLR5Z` | `admin.pol-is.jp` | S3 REST エンドポイント `admin.pol-is.jp.s3.ap-northeast-3.amazonaws.com`（OAC `polisjapan-admin-oac`、SigV4 で常に署名） | `PriceClass_200` | 無効 |
| `E2X1TX47YAAO8F` | `contact.pol-is.jp` | API Gateway `7r1e9gjfmk.execute-api.us-east-1.amazonaws.com`、オリジンパス `/production`（HTTPS） | `PriceClass_All` | 有効 |
| `E2VD4O5M17XG0X` | `share.pol-is.jp` | API Gateway `jh9u2wjvea.execute-api.us-east-1.amazonaws.com`、オリジンパス `/Production`（HTTPS） | `PriceClass_All` | 有効 |

ビヘイビアとキャッシュポリシーは次のとおり。

| ディストリビューション | パス | 許可メソッド | キャッシュポリシー | その他 |
| --- | --- | --- | --- | --- |
| LP | 既定 | GET, HEAD | `Managed-CachingOptimized` | 圧縮あり |
| WEB アプリ | `/csv/*` | GET, HEAD | `polisjapan-csv-versioned`（独自） | 圧縮あり |
| WEB アプリ | 既定 | GET, HEAD | `Managed-CachingOptimized` | 圧縮あり |
| 管理画面 | 既定 | GET, HEAD | `Managed-CachingOptimized` | viewer-request に CloudFront Function `polisjapan-admin-ip-check`。ルートオブジェクト `index.html` |
| お問い合わせ | 既定 | すべて | `Managed-CachingDisabled` | オリジンリクエストポリシー `Managed-AllViewerExceptHostHeader` |
| 共有リンク | 既定 | すべて | `Managed-CachingDisabled` | オリジンリクエストポリシー `Managed-AllViewerExceptHostHeader` |

**独自キャッシュポリシー `polisjapan-csv-versioned`**: TTL は最小 0 秒、既定 300 秒、最大 300 秒。キャッシュキーに含めるのはクエリ文字列 `_v` だけで、Cookie とヘッダは含めない（gzip と Brotli の圧縮は有効）。クライアント（`Client/public_html_app/javascript/common.js`）は CSV の URL に 5 分ごとに変わる `?_v=` を付けて取得するので、5 分ごとに全エッジで新しいキャッシュに切り替わる。バッチは CSV を `Cache-Control: max-age=300` 付きでアップロードする。この仕組みにより、CSV の更新に CloudFront の無効化を使わない（§12）。

**CloudFront Function `polisjapan-admin-ip-check`**（ランタイム `cloudfront-js-2.0`、コードは `Infra/terraform/modules/admin-site/ip_check.js.tftpl`）: 接続元の IP が許可リスト（CIDR）に含まれていなければ 403 を返す。IPv6 の接続は常に拒否する。許可リストは Terraform の変数 `admin_allow_ips` から、apply のときにコードへ埋め込まれる。同じリストは api Lambda の環境変数 `ADMIN_ALLOW_IPS` にも入り、管理 API 側でも検査する。

キャッシュの無効化は 2 か所で行う。デプロイのワークフローは LP・WEB アプリ・管理画面の 3 つを `/*` で無効化する。api Lambda は、テーマを削除したときに WEB アプリのディストリビューションの 2 パス（そのテーマのレポート CSV と `themes.csv`）だけを無効化する。

## 5. バッチ

### 5.1 Lambda

| 項目 | `polisjapan-batch-update` | `polisjapan-batch-create` |
| --- | --- | --- |
| 役割 | pol.is から集計を取得し、S3 の CSV を更新する | 承認済みの下書きを Selenium で pol.is に作成する（1 回の起動で 1 件） |
| イメージ | ECR `polisjapan-api`（api と同じイメージ） | ECR `polisjapan-batch-create`（Chrome for Testing 入り。ビルド元は `Server/web/Dockerfile.lambda-chromium`） |
| 起動コマンド | `api.lambda_handlers.batch_update.handler` | `api.lambda_handlers.batch_create.handler` |
| メモリ | 512 MB | 2048 MB |
| タイムアウト | 900 秒 | 900 秒 |
| アーキテクチャ | x86_64 | x86_64 |
| 同時実行数の予約 | 1 | 1 |
| 実行ロール | `polisjapan-batch-update-role` | `polisjapan-batch-create-role` |

同時実行数の予約を 1 にしているのは、前回の実行が長引いても次の起動と並走させないためである（`themes.csv` の書き込みや pol.is への二重投稿を防ぐ）。

環境変数は §4.2 の共通の環境変数に、次の 3 つを加えたものである。

| 名前 | 内容 | 出どころ |
| --- | --- | --- |
| `POLIS_LOGIN_USER` | pol.is のログインユーザー | SSM `/polisjapan/polis-login-user` |
| `POLIS_LOGIN_PASSWORD` | pol.is のログインパスワード | SSM `/polisjapan/polis-login-password` |
| `ALERTS_TOPIC_ARN` | 滞留リマインドの通知先（大阪の SNS `polisjapan-alerts`） | `monitoring` モジュール |

2 つの関数は同じ環境変数を持つが、SNS への発行権限は batch-create にしか無い（§9.2）。

### 5.2 EventBridge Scheduler

| スケジュール | 対象 | 間隔 | 状態 |
| --- | --- | --- | --- |
| `polisjapan-batch-update-schedule` | `polisjapan-batch-update` | 5 分（`rate(5 minutes)`） | ENABLED |
| `polisjapan-batch-create-schedule` | `polisjapan-batch-create` | 15 分（`rate(15 minutes)`） | ENABLED |

どちらもスケジュールグループ `default`、柔軟な時間枠はオフ、デッドレターキューなし。起動には IAM ロール `polisjapan-scheduler-invoke`（2 つの関数への `lambda:InvokeFunction` だけを許可）を使う。状態は Terraform の変数 `scheduler_state` で切り替える。

**再試行**: Scheduler 側の再試行回数は 0 回（`maximum_retry_attempts = 0`）。失敗しても次の定時起動に任せ、重複実行を避けるためである。ただし Scheduler は Lambda を非同期で呼び出すので、関数の実行が失敗すると Lambda の非同期呼び出しの再試行（既定で最大 2 回）は働く。関数ごとの非同期呼び出し設定（EventInvokeConfig）は作っておらず、既定値のままである。

アプリが起動されたときに何をするかは `docs/サーバー設計.md`、反映後の確認や失敗時の対応は [運用手順書.md](運用手順書.md) を参照。

| 暗号化 | AWS 所有キー（既定） |

項目の属性と状態の意味は `docs/データ仕様.md` を参照。

### 6.2 アーカイブ用 S3

`polisjapan-archive`（ap-northeast-3）は、保全用のデータを置くバケットである。ブロックパブリックアクセスをすべて有効、SSE-S3（AES256）で暗号化、バージョニング有効。ライフサイクルルール `to-glacier-ir` で、全オブジェクトを 90 日後に S3 Glacier Instant Retrieval へ移す。`prevent_destroy` で削除を拒否している。どのアプリからも読み書きしない。

### 6.3 ECR

| リポジトリ | 中身 | 使う Lambda |
| --- | --- | --- |
| `polisjapan-api` | `Server/web/Dockerfile.lambda` のイメージ | `polisjapan-api`、`polisjapan-batch-update` |
| `polisjapan-batch-create` | `Server/web/Dockerfile.lambda-chromium` のイメージ | `polisjapan-batch-create` |

どちらも ap-northeast-3 にあり、push 時のスキャン（基本スキャン）が有効、タグは上書き可能（MUTABLE）、暗号化は AES256。ライフサイクルポリシーで、タグの有無にかかわらず直近 5 イメージだけを残し、それより古いものは自動で削除する。CI はコミット SHA をタグにして push するので、切り戻しに使えるのは直近 5 回分のデプロイである。

## 7. シークレット

シークレットは SSM Parameter Store（ap-northeast-3）に SecureString（AWS 管理キー）で置く。

| パラメータ名 | 注入先の環境変数 | 注入先の Lambda |
| --- | --- | --- |
| `/polisjapan/openai-api-key` | `OPENAI_API_KEY` | 3 つすべて |
| `/polisjapan/langsmith-api-key` | `LANGCHAIN_API_KEY` | 3 つすべて |
| `/polisjapan/batch-access-key` | `BATCH_ACCESS_KEY` | 3 つすべて |
| `/polisjapan/user-access-key` | `USER_ACCESS_KEY` | 3 つすべて |
| `/polisjapan/encrypt-salt` | `ENCRYPT_SALT` | 3 つすべて |
| `/polisjapan/polis-login-user` | `POLIS_LOGIN_USER` | batch-update、batch-create |
| `/polisjapan/polis-login-password` | `POLIS_LOGIN_PASSWORD` | batch-update、batch-create |

**注入の仕組み**: Terraform の `data` モジュールがパラメータの器を初期値 `CHANGEME` で作り、値の変更は無視する（`ignore_changes`）。実際の値は人が AWS CLI で書き込む。`terraform apply` のとき、`Infra/terraform/environments/production/main.tf` の `data "aws_ssm_parameter" "secrets"` が値を読み、Lambda の環境変数に入れる。値が `CHANGEME` のままだと apply は失敗する（`postcondition`）。

この仕組みから、次のことが言える。

- Lambda は実行中に SSM を読まない。値を変えたら `terraform apply` をしないと反映されない（手順は [運用手順書.md](運用手順書.md) §5.5）。
- 復号した値が tfstate と Lambda の環境変数に入る。tfstate のバケットは非公開・暗号化・バージョニング有効を保つ（§11.2）。
- Lambda の実行ロールには `ssm:GetParameter` / `ssm:GetParameters` の権限があるが、アプリのコードは SSM を読んでいない。

パラメータの一覧は次で確認できる（値は取得しない）。

```sh
aws ssm describe-parameters --profile inventory --region ap-northeast-3 --query 'Parameters[].Name'
```

## 9. 権限（IAM）

### 9.1 GitHub Actions（OIDC）

GitHub Actions は長期のアクセスキーを使わず、OIDC で一時的な認証情報を得る。OIDC プロバイダは `token.actions.githubusercontent.com`（オーディエンス `sts.amazonaws.com`）。2 つのロールの信頼ポリシーは、`sub` が `repo:PolisJAPAN/PolisJAPAN:ref:refs/heads/main` のトークンだけを受け付ける。つまり、このリポジトリの `main` ブランチで動くワークフローしかロールを引き受けられない（フォークやほかのブランチ、プルリクエストからは不可）。定義は `Infra/terraform/environments/production/github_actions.tf`。

| ロール | 使うワークフロー | 許可 |
| --- | --- | --- |
| `polisjapan-gha-deploy-client` | `.github/workflows/deploy-client.yml` | 3 バケット（`pol-is.jp`、`app.pol-is.jp`、`admin.pol-is.jp`）の `s3:ListBucket`、オブジェクトの `s3:PutObject` / `s3:DeleteObject`。CloudFront 3 つ（LP・WEB アプリ・管理画面）の `cloudfront:CreateInvalidation`。**`app.pol-is.jp/csv/*` への `PutObject` / `DeleteObject` は明示的に拒否** |

Lambda の実行ロールには AWS の管理ポリシーを付けず、インラインポリシーだけで権限を与えている。ロググループは Terraform が先に作るので、`logs:CreateLogGroup` は許可していない。

| 自分のロググループへの `logs:CreateLogStream`、`logs:PutLogEvents` | あり | あり | あり |
| `app.pol-is.jp` の `s3:GetObject` / `PutObject` / `DeleteObject` / `ListBucket` | あり | あり | あり |
| `polisjapan-drafts` とその GSI の `dynamodb:GetItem` / `PutItem` / `UpdateItem` / `Query` / `Scan` | あり | あり | あり |
| `/polisjapan/*` の 7 パラメータの `ssm:GetParameter` / `GetParameters` | あり | あり | あり |

### 9.3 人が使う IAM ユーザーと CLI プロファイル

| AWS CLI プロファイル | IAM ユーザー | 権限 | 用途 |
| --- | --- | --- | --- |
| `inventory` | `inventory-readonly` | 管理ポリシー `ReadOnlyAccess`、`AWSBillingReadOnlyAccess` | 調査・確認。変更はできない |

### 10.2 CloudWatch アラーム

すべてのアラームは、ALARM になったときと OK に戻ったときの両方で、同じリージョンの SNS `polisjapan-alerts` に通知する。

| アラーム名 | リージョン | メトリクス | 条件 | データ欠落時 |
| --- | --- | --- | --- | --- |
| `polisjapan-api-healthcheck-failed` | us-east-1 | `AWS/Route53` `HealthCheckStatus`（最小値、60 秒） | 1 未満が 3 期間続く | 異常とみなす |
| `polisjapan-api-errors` | ap-northeast-3 | `AWS/Lambda` `Errors`（合計、300 秒、`FunctionName = polisjapan-api`） | 1 以上が 1 期間 | 正常とみなす |
| `polisjapan-batch-update-errors` | ap-northeast-3 | 同上（`polisjapan-batch-update`） | 1 以上が 1 期間 | 正常とみなす |
| `polisjapan-batch-create-errors` | ap-northeast-3 | 同上（`polisjapan-batch-create`） | 1 以上が 1 期間 | 正常とみなす |
| `polisjapan-batch-create-failed-drafts` | ap-northeast-3 | `PolisJAPAN/Batch` `FailedDrafts`（最大値、1800 秒） | 1 以上が 1 期間 | 状態を維持する |
| `polisjapan-batch-create-stalled` | ap-northeast-3 | 式 `IF(pending >= 1 AND published < 1, 1, 0)`。`pending` は `PendingDrafts` の最小値、`published` は `PublishedDrafts` の合計（どちらも 7200 秒） | 1 以上が 1 期間（投稿待ちがあるのに 2 時間 1 件も投稿できていない） | 状態を維持する |
| `polisjapan-batch-create-no-report` | ap-northeast-3 | `PolisJAPAN/Batch` `PendingDrafts` のサンプル数（3600 秒） | 1 未満が 1 期間（1 時間報告が無い） | 異常とみなす |

`polisjapan-batch-create-` で始まる 3 つは、Errors のアラームを補うためにある。失敗した下書きが隔離されると batch-create は正常終了になり、Errors のアラームはすぐ OK に戻るので、件数で滞留を見張る。API は例外を捕捉して 500 を返すため、API のアプリ内のエラーは `polisjapan-api-errors` に数えられない。API の 5xx を直接監視するアラームは無い。

アラームが鳴ったときの見方と対応は [運用手順書.md](運用手順書.md) §4、§5 を参照。アラームの一覧と現在の状態は次で確認できる。

```sh
aws cloudwatch describe-alarms --profile inventory --region ap-northeast-3 --query 'MetricAlarms[].[AlarmName,StateValue]' --output table
aws cloudwatch describe-alarms --profile inventory --region us-east-1 --query 'MetricAlarms[].[AlarmName,StateValue]' --output table
```

### 10.3 カスタムメトリクス

batch-create は起動のたびに、Embedded Metric Format（ログへの出力）で次のメトリクスを送る（`Server/web/api/lambda_handlers/backlog_monitor.py`）。名前空間は `PolisJAPAN/Batch`、ディメンションは `FunctionName = polisjapan-batch-create`。

| メトリクス | 内容 |
| --- | --- |
| `FailedDrafts` | 投稿に失敗して隔離された（FAILED の）下書きの件数 |
| `PendingDrafts` | 投稿待ち（APPROVED）の下書きの件数 |
| `PublishedDrafts` | その起動で投稿できた件数 |

FAILED の下書きが残っている間は、batch-create が毎朝 9 時台（JST）の最初の起動で、大阪の SNS `polisjapan-alerts` へタイトル一覧つきのリマインドを発行する。

### 10.4 SNS

### 11.2 state

state は S3 バケット `polisjapan-tfstate`（ap-northeast-3）のキー `production/terraform.tfstate` に置く。backend の暗号化を有効にし、ロックは S3 のロックファイル（`use_lockfile`）で行う（DynamoDB のロックテーブルは使わない）。バケットはブロックパブリックアクセスをすべて有効、SSE-S3 で暗号化、バージョニング有効で、バケットポリシーは無い。

state には SSM から読んだシークレットの復号値が入る（§7）。このバケットは Terraform 自身の state を置く場所なので、Terraform では管理していない。

`api` モジュールは変数 `api_image_uri` が空なら、`batch` モジュールは `api_image_uri` と `batch_create_image_uri` のどちらかが空なら作られない（`count`）。どちらも本番では設定済みである。

管理しているリソースの一覧は、`terraform` プロファイルで `terraform state list` を実行して確認する。

### 11.4 Terraform で管理していないもの

| 対象 | 理由 |
| --- | --- |
| tfstate バケット `polisjapan-tfstate` | state 自身の置き場所で、自己参照になるため |
| Lambda 3 つのコンテナイメージ（`image_uri`） | `ignore_changes`。イメージの更新は CI が行い、apply で巻き戻さないため |
| contact / share の Lambda のコード、実行ロール、REST API の定義 | §8.3 |
| SSM パラメータの値 | `ignore_changes`。値をコードに書かないため |
| SES のメールアドレス ID | 個人のアドレスをコードに残さないため |
| IAM ユーザー（`terraform-deploy`、`inventory-readonly` など） | Terraform を実行する権限を Terraform 自身で壊す事故を防ぐため |
| API Gateway のアカウント設定と、REST API の実行ログのロググループ（us-east-1） | 手動で作られたまま取り込んでいない |

このほか、現在のシステムが使っていない手動作成のリソースが残っている。IAM ロール `PolisJAPAN-Reboot-role-h4e3u7x1`、`SystemManagerAccess`、`Amazon_EventBridge_Invoke_Automation_1662815998`、`rds-monitoring-role`、`CloudWatchSyntheticsRole-polis-japan-api-healt-41a-19ebc5f32482` と、大阪のロググループ `/aws/lambda/cwsyn-polis-japan-api-healt-` で始まる 2 つ（保持期間なし）である。どれも Terraform の管理外で、現在の構成から参照されていない。

### 11.5 データを守る設定

`prevent_destroy` を付けているのは、S3 `pol-is.jp`、`app.pol-is.jp`、`polisjapan-archive`、Route53 ゾーン `pol-is.jp`、DynamoDB `polisjapan-drafts` である。これらを削除する plan は Terraform 自身がエラーにする。ACM 証明書には `create_before_destroy` を付け、作り直すときに CloudFront や API Gateway が参照中の証明書を先に消さないようにしている。

## 12. 費用に効く設計

運用費を小さく保つために、次の選択をしている。設計判断の全体は [アーキテクチャ.md](アーキテクチャ.md) §5 にある。

| 選択 | 理由 |
| --- | --- |
| 常時起動のサーバー、VPC、NAT ゲートウェイを持たない | 利用量が小さく、Lambda・DynamoDB・EventBridge Scheduler の従量課金にすると固定費がほぼ無くなる |
| CSV の更新は CloudFront の無効化ではなく TTL（300 秒）と `_v` クエリで反映する | 5 分ごとに無効化すると月の無料枠を超えて費用がかかる。無効化はテーマ削除時の 2 パスだけにしている（§3.2） |
| 死活監視は Route53 のヘルスチェックで行う | HTTP の応答確認で足り、ブラウザを動かす監視（CloudWatch Synthetics の Canary）より大幅に安い。HTTPS で確認するので証明書の失効も検知できる |
| 管理画面の IP 制限は WAF ではなく CloudFront Function で行う | WAF は固定費がかかり、CloudFront Function は実質無料。API 側でも同じ許可リストを検査する |
| Provisioned Concurrency を使わない | 初回の応答が数秒遅くなるが、常時の費用をかけない |
| DynamoDB はオンデマンド課金 | 下書きの読み書きが少なく、容量を確保する固定費をかけないため |
| ログの保持は 30 日、ECR は直近 5 イメージ、`app.pol-is.jp` の古いバージョンは 7 日で削除、アーカイブは 90 日後に Glacier Instant Retrieval | 保存料が際限なく増えないようにする |

実際の費用は AWS の請求（Cost Explorer）で確認する。`inventory` プロファイルには請求の読み取り権限がある。
