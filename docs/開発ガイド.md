# PolisJAPAN 開発ガイド

開発を始める手順と、変更を本番に届けるまでの流れをまとめる。実装の詳細は `docs/サーバー設計.md` と `docs/クライアント設計.md`、本番への反映と障害対応は `docs/運用手順書.md` を参照。

## 1. 必要なもの

| もの | 用途 |
| --- | --- |
| Git | ソースコードの取得 |
| Docker Desktop | ローカル環境（サーバーもクライアントもコンテナで動かす） |
| Python 3 | 文書の検査（`scripts/check_docs.py`。標準ライブラリだけで動く） |
| AWS CLI と認証情報 | 本番の調査とインフラの変更をする人だけ。プロファイルは `inventory`（読み取り専用）と `terraform`（管理者） |
| Terraform | インフラを変更する人だけ |

## 2. 最初の準備

```sh
git clone <このリポジトリ>
cd PolisJAPAN
git config core.hooksPath .githooks   # コミット時の文書検査を有効にする（クローンごとに一度）
```

## 3. ローカル環境

### 3.1 クライアント（LP・WEB アプリ・管理画面）

```sh
cd Client
docker-compose up
```

| URL | サイト |
| --- | --- |
| http://localhost:8080/ | LP |
| http://localhost:8081/ | WEB アプリ |
| http://localhost:8082/ | 管理画面 |

ローカルの画面は、本番の CSV と API を使って動く。そのため、ローカルからでも本番に影響する操作がある（テーマの投稿、お問い合わせの送信、管理画面の操作など）。試してよい操作と注意点は `docs/クライアント動作確認ガイド.md` を必ず読むこと。

スタイルは `Client/scss/` を編集し、ビルドした CSS もコミットする。ビルドの方法は `docs/クライアント設計.md` と `Client/README.md`。

### 3.2 サーバー（API・バッチ）

```sh
cd Server
docker-compose up
```

FastAPI、nginx、MySQL などのコンテナが起動する。API は http://localhost/ で応答し、http://localhost/docs で各 API を試せる。ローカルでは下書きを MySQL に保存する（本番は DynamoDB）。

AI 生成などシークレットが必要な機能を動かすには、`Server/web/.env.example` を `Server/web/.env` にコピーして値を入れる。`Server/web/.env` はコミットしない。

テストは `Server/web` で `pytest` を実行する。構成と実行方法の詳細は `docs/サーバー設計.md`。

### 3.3 インフラ

`Infra/terraform/README.md` と `docs/インフラ構成.md` を参照。ローカルで動かす環境は無く、変更は本番に対して `terraform plan` で差分を確かめてから適用する。

## 4. 変更の流れ

1. `main` から作業用のブランチを作る。
2. 変更し、ローカルで動作を確かめる。画面の変更は、ブラウザで実際の表示と操作を確認する。
3. 同じコミットで、対応する文書を更新する（§5）。
4. コミットする。コミット時に文書の検査が走る。
5. push してプルリクエストを作る。プルリクエストでも文書の検査が走る。
6. `main` にマージする。`Client/public_html*/**` か `Server/web/**` に変更があれば、本番に自動でデプロイされる。
7. 反映後の確認をする（`docs/運用手順書.md` §2.4）。

`main` へのマージは本番への反映と同じ意味を持つ。マージの前に、反映される内容を確認すること。

### コミットメッセージ

1 行目は `種別: 内容` の形で、日本語で書く。種別は `feat`（機能追加）、`fix`（修正）、`docs`（文書）、`refactor`、`test`、`chore` など。

## 5. 文書の更新

`docs/` の文書は、このシステムの正本である。コードを変えたら、同じコミットで対応する文書を更新する。

| 変更したもの | 更新する文書 |
| --- | --- |
| 画面、クライアントの JS・SCSS | `docs/画面仕様書.md`、`docs/クライアント設計.md`。操作やテストに関わるなら `docs/操作ユースケース.md`、`docs/本番定期テストケース.md` |
| API の入出力 | `docs/API仕様.md` |
| CSV、DynamoDB、ブラウザに保存するデータ | `docs/データ仕様.md` |
| サーバーの処理、バッチ、コンテナイメージ | `docs/サーバー設計.md` |
| AWS のリソース、Terraform | `docs/インフラ構成.md`、`Infra/terraform/README.md` |
| デプロイや運用の手順、アラーム | `docs/運用手順書.md` |
| 全体の構成、設計判断 | `docs/アーキテクチャ.md` |

- 不具合や未対応の点を見つけたら `docs/改善バックログ.md` に足す。直したら消す。
- 文書に影響しない変更（リファクタリングなど）は、コミットメッセージに `Docs: 変更不要（理由）` を入れる。
- 検査は `python3 scripts/check_docs.py` で手元でも実行できる。検査の内容と書き方の規則は `docs/README.md`。

## 6. 本番でやってはいけないこと

- `/theme/post_draft` にテスト送信しない。審査なしで実際のテーマが公開される。ローカルの画面からの投稿も、本番の API に届く。
- S3 の `csv/` 配下を手で同期・上書きしない。バッチが管理する本番のデータである。
- シークレットの値、IP 許可リスト、個人のメールアドレスをコミットしない。
- 本番の画面で試してよい操作は `docs/本番定期テストケース.md` に従う。
