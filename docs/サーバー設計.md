# PolisJAPAN サーバー設計

サーバー側のコード（`Server/`）が、どこで何を実装していて、どう動くかを記述する。API ごとの入出力とエラーは `docs/API仕様.md`、CSV と DynamoDB の項目定義は `docs/データ仕様.md`、AWS リソースの設定（Lambda のメモリ、スケジュール、IAM、アラーム）は `docs/インフラ構成.md`、本番での操作手順は `docs/運用手順書.md` を参照。

## 1. 全体像

サーバーのコードは 1 つの Python パッケージ `api`（`Server/web/api/`）にまとまっている。同じコードから 3 つの Lambda が動く。

| Lambda | 入口（ハンドラ） | コンテナイメージ | 起動のされ方 |
| --- | --- | --- | --- |
| api | `api.main.handler`（FastAPI を Mangum で包んだもの） | `Server/web/Dockerfile.lambda` | API Gateway 経由の HTTP リクエスト |
| batch-update | `api.lambda_handlers.batch_update.handler` | `Server/web/Dockerfile.lambda`（api と同じイメージ） | EventBridge Scheduler が 5 分ごとに直接起動 |
| batch-create | `api.lambda_handlers.batch_create.handler` | `Server/web/Dockerfile.lambda-chromium` | EventBridge Scheduler が 15 分ごとに直接起動 |

ハンドラの指定は Terraform 側の `image_config.command` で行い、イメージ自体の `CMD` は既定値にすぎない。ローカルでは同じ FastAPI アプリを uvicorn で起動する（§12）。

これとは別に、お問い合わせフォームの送信先として独立した Lambda（`Server/lambda/contact/`）がある（§11）。

| AI | LangChain 0.3.27（langchain-core 0.3.78、langchain-openai 0.3.35、langchain-community 0.3.31）、LangSmith 0.4.33（プロンプトの取得）、OpenAI の GPT-5 系モデル |

## 3. ディレクトリ構成と各層の責務

### 3.1 `Server/` 直下

| パス | 内容 |
| --- | --- |
| `Server/web/` | API とバッチのアプリ本体。コンテナイメージの定義、テスト、移行スクリプトを含む |
| `Server/lambda/contact/` | お問い合わせ Lambda のコード（`Server/lambda/contact/lambda_function.py`）と手動デプロイ手順（`Server/lambda/contact/README.md`） |
| `Server/admin/` | ローカルの nginx が `/dashboard/` で配信する管理画面のコピー。HTML・JS・CSS は `Client/public_html_admin/` と同一内容（画像のみ差分あり）。本番の管理画面は `Client/public_html_admin/` から配信される |
| `Server/nginx/default.conf` | ローカル用 nginx の設定。`/dashboard/` を `Server/admin/` から返し、それ以外を web コンテナの 8000 番へ転送する |
| `Server/docker-compose.yml` | ローカル開発環境（web・nginx・db・cache）の定義（§12） |
| `Server/.env` | docker-compose が読む変数ファイル。`PROJECT_NAME` だけを持ち、コンテナ名の接頭辞に使う。シークレットは置かない |

### 3.2 `Server/web/` 直下

| パス | 内容 |
| --- | --- |
| `Server/web/api/` | アプリのパッケージ（§3.3） |
| `Server/web/scripts/` | 運用スクリプト。現在は `Server/web/scripts/migrate_drafts_to_dynamodb.py`（MySQL の `t_draft` を JSON から DynamoDB へ書き込み、件数と全属性を突き合わせる。`origin_html` は移さない）のみ |
| `Server/web/tests/` | pytest のテスト（§12.3） |
| `Server/web/Dockerfile` | ローカル開発用イメージ（§10） |
| `Server/web/Dockerfile.lambda` | Lambda「api」「batch-update」共用イメージ |
| `Server/web/Dockerfile.lambda-chromium` | Lambda「batch-create」用イメージ（Chrome 同梱） |
| `Server/web/pyproject.toml`、`Server/web/poetry.lock` | 依存の宣言とロック。pytest の設定（`testpaths = ["tests"]`、`asyncio_mode = "auto"`）もここにある |
| `Server/web/.env.example` | ローカル用シークレットの雛形。コピーして `Server/web/.env` を作る（コミットしない） |

### 3.3 `Server/web/api/` の各層

| パス | 責務 |
| --- | --- |
| `Server/web/api/main.py` | FastAPI アプリの組み立て。ミドルウェア、ルーターのマウント、Swagger の公開可否、Lambda 用の `handler` |
| `Server/web/api/routers/` | URL ごとの処理。入力の取り出し、アクセスキー・IP の検査、サービスとストアの呼び出し、レスポンスの組み立て。マウントされるのは `admin.py`・`batch.py`・`theme.py` の 3 つ。`user.py` は未マウント（§13） |
| `Server/web/api/schemas/` | ルーターごとのリクエスト・レスポンスの Pydantic モデルと、API 固有のエラー（`ApiError` の派生クラス）。リクエストは各クラスの `parse()` がフォーム値（`Form`）から組み立てる |
| `Server/web/api/services/` | 業務処理。`theme.py`（AI 生成）、`batch.py`（CSV 更新と pol.is への投稿）、`admin.py`（中身なし）、`user.py`（休眠）。いずれも `CommonService` を継承する |
| `Server/web/api/repositories/` | 下書きの保存先の抽象化（`DraftStore`）と、DynamoDB 実装・MySQL 実装（§6） |
| `Server/web/api/cruds/` | SQLAlchemy による MySQL のテーブル操作。`t_draft.py` は MySQL 版の下書きストアが使う。`t_account.py`・`t_user.py`・`t_user_add.py` は休眠中の `user` 機能用 |
| `Server/web/api/models/` | `tables.py`（SQLAlchemy のテーブル定義と、レスポンス用の Pydantic モデル `TDraftModel` など）、`types.py`（下書きの投稿状態 `PostStatus`、ログレベル `LogLevel`） |
| `Server/web/api/core/` | 全 API 共通の土台。`common_route.py`（前処理・後処理・例外処理、§4）、`common_service.py`（サービスの基底クラスと動的生成）、`common_schema.py`（`ApiError` と共通エラー）、`common_cruds.py`（CRUD の基底クラス）、`middleware/timeout_middleware.py`（処理時間の上限） |
| `Server/web/api/configs/` | 環境ごとの設定（§5）。`user_auth.py` は休眠中のユーザー認証の対象外リスト |
| `Server/web/api/utils/` | 共通部品。`storage_s3.py`（S3・CloudFront、§9）、`web_loader_chrome.py`（Selenium の操作）、`web_loader_httpx.py`（httpx による GET）、`security.py`（IP 許可リストの判定、パスワードのハッシュ）、`csv.py`（CSV の解析と生成）、`common.py`（辞書リストのマージ・並べ替え）、`time.py`（JST の時刻と書式）、`error.py`（`trace_id` の生成）、`html_parser.py`（BeautifulSoup によるスクレイピング補助）、`drivers/database.py`（MySQL の非同期エンジンとセッション） |
| `Server/web/api/lambda_handlers/` | バッチ Lambda の入口。`batch_update.py`、`batch_create.py`、`backlog_monitor.py`（滞留監視、§8.5） |
| `Server/web/api/logger.py` | ログ出力（§4.4） |

処理の向きは「ルーター → サービス → ストア／ユーティリティ」で、ルーターは `request.state.service` に用意されたサービスと、`service.draft_store` に用意されたストアだけを使う。下書きの読み書きを直接 SQL や DynamoDB に書かないこと。

## 4. リクエスト処理の流れ

### 4.1 アプリの組み立て（`Server/web/api/main.py`）

1. 環境変数 `APP_ENV`（未設定なら `production` とみなす）で `create_app()` を呼ぶ。`APP_ENV` が `production` または `serverless` のときは `docs_url`・`redoc_url`・`openapi_url` を無効にし、Swagger（`/docs`、`/redoc`、`/openapi.json`）を公開しない。本番 Lambda は `serverless` で動く。`localhost` と `development` では公開する
2. `TimeoutMiddleware`（`Server/web/api/core/middleware/timeout_middleware.py`）を 300 秒で登録する。処理が 300 秒を超えると 504（`{"detail": "Request processing time excedeed limit"}`）を返す。ただし本番の api Lambda のタイムアウトはこれより短いので、本番では Lambda 側の制限が先に効く
3. `admin`・`batch`・`theme` の 3 ルーターをマウントする
4. CORS ミドルウェアを、環境ごとの `CORS_PARAMETERS`（§5）で登録する。後から追加したミドルウェアが外側になるため、リクエストは CORS → タイムアウト → ルートの順に通る

### 4.2 共通ルート（`Server/web/api/core/common_route.py`）

3 つのルーターはどれも `route_class=CommonRoute` を指定しており、すべての API が次の順で処理される。

1. URL のパスを `/` で分け、1 つ目をルーター名、2 つ目を API 名として `request.state` に入れる（例: `/admin/info` → `admin`・`info`）
2. `Server/web/api/configs/user_auth.py` の `is_user_auth_api()` でユーザー認証の要否を判定する。マウントされている `admin`・`batch`・`theme` は全 API が対象外なので、現在はどの API でもユーザー認証は行わない
3. `DATA_BACKEND` が `mysql` のとき（ローカル）は MySQL の非同期セッションを開く。`dynamodb` のとき（本番）は RDB を使わない
4. `get_service()` がルーター名からサービスクラスを動的に読み込む（`api.services.<ルーター名>` の `<ルーター名の先頭大文字>Service`）。続けて `initialize_utils()` で S3 クライアントを開く（バケットは環境変数 `CSV_BUCKET`、未設定なら `app.pol-is.jp`）
5. `create_draft_store()` で下書きストアを作り、サービスに持たせる（§6）
6. ルートの関数を実行する（フォーム値の取り出しと Pydantic の検証もここで行われる）
7. 正常終了でも例外でも、最後に `finalize_request()` が S3 クライアントと DB セッションを閉じる

### 4.3 例外の扱いと `trace_id`

- ルートの中で `ApiError`（`Server/web/api/core/common_schema.py`）の派生クラスが投げられると、そのクラスの `status_code` と `message` で JSON（`{"message", "trace_id"}`）を返す。481・482・483 などの独自ステータスはここから来る。各 API のエラーの一覧は `docs/API仕様.md`
- それ以外の例外はすべて 500（`{"message": "サーバー内部で予期しないエラーが発生しました。", "trace_id"}`）になる。入力検証の失敗、OpenAI や pol.is への通信失敗もここに含まれる
- `trace_id` はエラーの時点で `Server/web/api/utils/error.py` の `generate_trace_id()` が作る（16 桁のハッシュと 32 桁の乱数をハイフンでつないだもの）。同じ値をレスポンスとログの両方に出すので、利用者から受け取った `trace_id` で CloudWatch Logs を検索すれば、発生した API・例外の内容・スタックトレースが見つかる。正常なリクエストには `trace_id` は付かない
- 例外を API の中で捕まえて 500 を返すので、api Lambda の実行自体は成功扱いになる（Lambda の Errors には数えられない）

### 4.4 アクセスキーと IP の検査

検査は共通処理ではなく、各ルートの関数の冒頭に書かれている。

| ルート | 検査 |
| --- | --- |
| `/theme/generate_axis`、`/theme/generate_comments`、`/theme/generate_descriptions` | フォームの `access_key` が `USER_ACCESS_KEY` と一致しなければ 481 |
| `/theme/post_draft` | `access_key` は必須項目として受け取るが、値を照合していない |
| `/batch/update`、`/batch/create_all`、`/batch/delete` | `access_key` が `BATCH_ACCESS_KEY` と一致しなければ 481。IP の検査は無い |
| `/batch/healthcheck` | 検査なし |
| `/admin/info`、`/admin/approve`、`/admin/edit` | まず `access_key` を `BATCH_ACCESS_KEY` と照合し（不一致は 481）、次に接続元 IP を `ADMIN_ALLOW_IPS` と照合する（不一致は 482） |

IP の照合は `Server/web/api/utils/security.py` の `Security.is_allowed_ip()` が行い、単一の IP と CIDR 表記の両方を受け付ける（不正な書式の要素は無視する）。照合に使う接続元は `request.client.host` で、本番では Mangum が API Gateway（HTTP API）のイベントの `requestContext.http.sourceIp` から設定した値、ローカルでは nginx コンテナの IP になる。

バッチの Lambda ハンドラはアクセスキーを検査しない（起動できるのが IAM で許可された Scheduler だけのため）。

### 4.5 ログ

- `Server/web/api/logger.py` の `Logger` が `[YYYY-MM-DD HH:MM:SS] [レベル] メッセージ` の形で標準出力（ERROR 以上は標準エラー）に出す。時刻は JST。端末向けの ANSI 色コードが常に付くので、CloudWatch Logs 上では行頭と行末に制御文字が見える
- 各 API の開始・終了とルーター名・API 名、エラー時の詳細は INFO で出る。エラーの詳細も INFO で出力している
- レベルごとの出力可否は `LOG_ENABLE_FLAGS` で決まる。ローカルの設定はすべて有効。本番（`serverless`）は環境変数 `LOG_ENABLE_FLAGS`（JSON）から読むが、JSON のキーは文字列になり、整数のログレベルと一致しないため、この環境変数では出力を止められない。結果として本番でも DEBUG を含む全レベルが出力される
- Lambda の標準出力はそのまま CloudWatch Logs の `/aws/lambda/<関数名>` に入る
- ローカルの MySQL エンジンは `echo=True` なので、発行した SQL もすべてログに出る

## 5. 設定の仕組み

### 5.1 `APP_ENV` と環境フォルダ

`Server/web/api/configs/__init__.py` が import 時に環境変数 `APP_ENV` を読み、対応するフォルダの 3 ファイルを読み込む。`APP_ENV` が未設定なら `development` を使い、一覧に無い値なら `ValueError` で起動に失敗する。

| `APP_ENV` | フォルダ | 使われる場所 |
| --- | --- | --- |
| `serverless` | `Server/web/api/configs/serverless/` | 本番の 3 つの Lambda（Terraform が環境変数で設定） |
| `localhost` | `Server/web/api/configs/localhost/` | ローカルの docker-compose（`Server/docker-compose.yml` で設定）とテスト（`Server/web/tests/conftest.py` が既定値として設定） |
| `production` | `Server/web/api/configs/production/` | リポジトリ内に、この値で起動する設定は無い。中身は `development` とほぼ同じで、ローカル向けの既定値を持つ |
| `development` | `Server/web/api/configs/development/` | `APP_ENV` 未設定時の読み込み先。この値を明示する設定はリポジトリ内に無い |

各フォルダの役割は次のとおり。

| ファイル | 内容 |
| --- | --- |
| `constants.py` | `API_BASE_URL`、`CLIENT_BASE_URL`、`ENCRYPT_SALT`、`BATCH_ACCESS_KEY`、`USER_ACCESS_KEY`、`ADMIN_ALLOW_IPS`、`LOG_ENABLE_FLAGS`、`CORS_PARAMETERS`（`serverless` は `DATA_BACKEND` も） |
| `credentials.py` | `ENVBIRONMENT_VALIABLES`（綴りはコードのまま）。ここに書いた値は import 時に `os.environ` へ書き込まれ、LangChain や boto3 が環境変数として読む |
| `database.py` | MySQL の接続先（ホスト・DB 名・ユーザー・ポート・パスワード） |

共通の `Server/web/api/configs/constants.py` を先に読み、環境フォルダの `constants.py` で上書きしたものが `configs.constants` になる。共通側には数値型の上限値、区切り文字 `SPLITTER`（`###br###`）、`DATA_BACKEND = "mysql"`、`PUBLISH_RETRY_LIMIT = 9` がある。

各フォルダには `cache.py`（memcached の接続先）もあるが、どこからも読まれていない。

### 5.2 本番（`serverless`）

- 設定ファイルに値を持たない。`Server/web/api/configs/serverless/constants.py` が Lambda の環境変数から組み立てる。`API_BASE_URL`・`CLIENT_BASE_URL`・`ENCRYPT_SALT`・`BATCH_ACCESS_KEY`・`USER_ACCESS_KEY` は必須で、1 つでも欠けると import 時に `KeyError` になり Lambda が起動しない。`ADMIN_ALLOW_IPS` と `CORS_ALLOW_ORIGINS` はカンマ区切りで読む。`DATA_BACKEND` は `dynamodb` に固定
- `credentials.py` は空で、`OPENAI_API_KEY`・`LANGCHAIN_API_KEY` などは Lambda の環境変数として直接渡される
- `database.py` は互換のために環境変数を読むだけで、実際には使われない
- シークレットの実体は SSM Parameter Store にあり、Terraform が `terraform apply` のときに Lambda の環境変数へ入れる。Lambda は実行中に SSM を読まない。どの変数がどのパラメータから来るかは `docs/インフラ構成.md`

コードが直接読む環境変数（設定ファイルを経由しないもの）は次のとおり。

| 環境変数 | 読む場所 | 未設定時 |
| --- | --- | --- |
| `CSV_BUCKET` | `Server/web/api/core/common_service.py` | `app.pol-is.jp`（本番のバケット） |
| `DRAFTS_TABLE` | `Server/web/api/repositories/draft_store_dynamo.py` | `polisjapan-drafts` |
| `CLOUDFRONT_DISTRIBUTION` | `Server/web/api/routers/batch.py`（`/batch/delete`） | 空なら CloudFront の無効化をしない |
| `POLIS_LOGIN_USER`、`POLIS_LOGIN_PASSWORD` | `Server/web/api/services/batch.py` | pol.is への投稿時に `RuntimeError` |
| `ALERTS_TOPIC_ARN` | `Server/web/api/lambda_handlers/backlog_monitor.py` | リマインドを送らない |
| `AWS_LAMBDA_FUNCTION_NAME` | `Server/web/api/utils/web_loader_chrome.py` | Lambda 用の Chrome 起動オプションを付けない |

pol.is のログイン情報と `ALERTS_TOPIC_ARN` はバッチの Lambda にだけ渡されており、api Lambda には無い。

### 5.3 ローカル（`localhost`）

- 設定ファイルはシークレットを環境変数から読み、無ければローカル専用の既定値を使う。そのため設定ファイルに実値は無く、コミットしてよい
- 実値は `Server/web/.env` に書く（雛形は `Server/web/.env.example`）。`Server/docker-compose.yml` が `env_file` として web コンテナに読み込む。ファイルが無くても起動はできる
- `Server/web/.env` に置くもの: `OPENAI_API_KEY`、`LANGCHAIN_API_KEY`、`LANGCHAIN_TRACING_V2`、AWS のアクセスキーとリージョン（S3 にアクセスする場合のみ）、`ENCRYPT_SALT`、`BATCH_ACCESS_KEY`、`USER_ACCESS_KEY`、`ADMIN_ALLOW_IPS`、`DB_PASSWORD`、`POLIS_LOGIN_USER`・`POLIS_LOGIN_PASSWORD`（ローカルで投稿を試す場合のみ）
- `ADMIN_ALLOW_IPS` の既定値はループバックと Docker の内部ネットワーク帯で、nginx 経由のアクセスが通る
- `localhost` の `credentials.py` は `LANGCHAIN_PROJECT` を `PolisJAPAN`、`LANGCHAIN_TRACING_V2` を既定で `true` にするので、ローカルの AI 生成は LangSmith にトレースが記録される。本番の Lambda の環境変数には `LANGCHAIN_TRACING_V2` が含まれていない
- S3 の認証は `APP_ENV` が `localhost` のときだけ環境変数のアクセスキーを明示的に使い、それ以外では実行環境の既定の認証（Lambda では IAM ロール）を使う（`Server/web/api/utils/storage_s3.py`）

## 6. 下書きストアの抽象化

テーマの下書きは、本番では DynamoDB、ローカルでは MySQL に保存する。ルーターとサービスはどちらかを意識せず、`Server/web/api/repositories/draft.py` の `DraftStore` だけを使う。

### 6.1 インターフェース

`DraftStore`（Protocol）のメソッドは次のとおり。

| メソッド | 用途 |
| --- | --- |
| `insert_draft` | 下書きの新規登録（`/theme/post_draft`） |
| `select_by_id` | 1 件取得。論理削除済みは返さない |
| `select_all` | 論理削除されていない全件（`/admin/info`） |
| `select_by_post_status` | 投稿状態で絞り込み（バッチ、滞留監視） |
| `update_post_status` | 投稿状態の変更。APPROVED にするときは `publish_retry_count` を 0 に戻す（DynamoDB 実装） |
| `increment_publish_retry` | 投稿失敗回数を 1 増やす |
| `update_content` | テーマ名・説明・初期コメント・カテゴリのうち、`None` でない項目だけを更新 |
| `update_post_info` | 投稿後の `conversation_id`・`report_id`・投稿状態の記録 |
| `delete_by_id` | 論理削除（`status` を 0 にする） |
| `commit`、`rollback` | MySQL のトランザクション操作。DynamoDB 実装では何もしない |

戻り値の型は `Draft`（dataclass）または MySQL の ORM オブジェクトで、どちらも `TDraftModel` と同じ属性名を持つため、レスポンスのモデルにそのまま渡せる。

### 6.2 切り替え

`create_draft_store(db_session)` が `configs.constants.DATA_BACKEND` を見て実装を選ぶ。`dynamodb` なら `DynamoDraftStore`、それ以外は `MySQLDraftStore`。`DATA_BACKEND` は共通設定で `mysql`、`serverless` でだけ `dynamodb` になるので、切り替えは `APP_ENV` で決まる。MySQL 実装は DB セッションが必須で、`None` を渡すと `ValueError` になる。そのため、セッションを渡さないバッチの Lambda ハンドラは `dynamodb` の環境でしか動かない。

### 6.3 DynamoDB 実装（`Server/web/api/repositories/draft_store_dynamo.py`）

- テーブル名は環境変数 `DRAFTS_TABLE`。主キー `id`（数値）と、GSI `post_status-index`（キー `post_status`）を使う。テーブルの定義は `docs/データ仕様.md` と `docs/インフラ構成.md`
- boto3 の同期クライアントを `asyncio.to_thread` で呼び、イベントループを止めない
- ID は登録時点の epoch 秒。同じ秒に登録が重なったら、存在しないことを条件にした `put_item` が失敗するので、1 を足して再試行する（最大 20 回）
- 一覧はスキャン／クエリの結果を `id` の昇順に並べ替えて返す。ID が登録時刻なので、昇順は古い順と同じ
- 日時は ISO 8601 の文字列で保存し、読むときに `datetime` に戻す
- 更新は `update_item` で該当項目と `update_date` だけを書き換える。即時に反映されるので `commit`・`rollback` は何もしない

### 6.4 MySQL 実装（`Server/web/api/repositories/draft_store_mysql.py`）

- `Server/web/api/cruds/t_draft.py` に処理を委ねる薄い層。テーブル `t_draft` の定義は `Server/web/api/models/tables.py`
- `t_draft` には `publish_retry_count` の列が無いので、`increment_publish_retry` はメモリ上で数を増やすだけで保存しない。ローカルでは FAILED への隔離（§8.4）が起きない
- `select_by_post_status` は並び順を指定していない
- テーブルを作る SQL やマイグレーションはリポジトリに無い。ローカルの MySQL に `t_draft` を作る手順は未確認

## 7. AI テーマ生成

WEB アプリのテーマ作成画面（AI アシスト）から 3 つの API が順に呼ばれる。実装は `Server/web/api/services/theme.py` の `ThemeService`。

### 7.1 段階と入出力

| 段階 | API | 入力 | 出力 |
| --- | --- | --- | --- |
| 1. 対立軸 | `/theme/generate_axis` | `theme` | 対立軸の文字列のリスト |
| 2. 意見 | `/theme/generate_comments` | `theme`、`axis`（対立軸を `###br###` でつないだ文字列） | 全対立軸分の意見を 1 つにまとめたリスト |
| 3. 説明 | `/theme/generate_descriptions` | `theme`、`axis`、`comments`（どちらも `###br###` 区切り） | 説明文の文字列 |

各段階の処理は次のとおり。いずれも LangChain の LCEL（`RunnableLambda` と `.assign()` の連結）で組み立てている。

1. **対立軸**（`generate_axis`）: テーマで DuckDuckGo のニュース検索を行い、結果の見出しと抜粋を背景情報にする → プロンプト `get_axis_standalone` でモデルを呼ぶ → 出力を行ごとに分け、各行の先頭の `- ` と前後の空白を取り除く。空の行は取り除いていない
2. **意見**（`generate_comments_for_axes`）: 対立軸ごとに「ニュース検索 → プロンプト `get_comments_standalone` → 行ごとに分割（空行は除く）→ 先頭の `- ` を除去」を行う。対立軸ごとの処理は `abatch()` で並列に実行し、同時実行数は 3。結果は対立軸の順に連結する
3. **説明**（`generate_description`）: ニュース検索 → 対立軸と意見を `- ` 付きの行に整形 → プロンプト `get_description_standalone` → 出力の文字列をそのまま返す

### 7.2 モデルとプロンプト

- 3 段階とも `ChatOpenAI(model="gpt-5-nano", reasoning_effort="low", verbosity="low")` を使う。認証は環境変数 `OPENAI_API_KEY`
- プロンプトはコードに持たず、実行のたびに LangSmith から取得する（`get_prompt_callable()` が `LangSmithClient().pull_prompt(<キー>)` を呼ぶ）。認証は環境変数 `LANGCHAIN_API_KEY`。プロンプトの文面を変えるときは LangSmith 上で編集し、デプロイは要らない。プロンプトの本文と、取得するバージョンの指定（タグやコミット）の運用は未確認
- 検索は `DuckDuckGoSearchResults(backend="news", output_format="list")`。検索語はテーマの文字列そのもの

### 7.3 失敗時の扱い

- ニュース検索が例外になったときは、背景情報を空にして生成を続ける（エラーにしない）
- LangSmith からのプロンプト取得や OpenAI の呼び出しが失敗したときは、例外がそのまま上がり、共通ルートが 500 と `trace_id` を返す（§4.3）。再試行は LangChain・SDK の既定の動作に任せており、アプリとしての再試行は無い
- 生成結果は保存しない。利用者が画面で編集したあと `/theme/post_draft` で送ると、初めて下書きとして保存される（投稿状態は APPROVED。§8.3 のバッチがそのまま pol.is に公開する）

## 8. バッチ

### 8.1 Lambda ハンドラと HTTP の `/batch/*` の関係

バッチの処理本体は `Server/web/api/services/batch.py` の `BatchService` にあり、本番の Lambda ハンドラと HTTP のルートが同じメソッドを呼ぶ。

| 処理 | 本番（定期実行） | HTTP（手動・ローカル） |
| --- | --- | --- |
| 投票情報の更新 `update_themes()` | `Server/web/api/lambda_handlers/batch_update.py`。5 分ごと | `/batch/update` |
| 承認済み下書きの投稿 `publish_approved_drafts()` | `Server/web/api/lambda_handlers/batch_create.py`。15 分ごと、1 回に 1 件（`limit=1`） | `/batch/create_all`。件数の上限なし（`limit=None`） |

違いは次のとおり。

- Lambda ハンドラは FastAPI を通らない。`BatchService` を直接作り、S3 クライアントを開き、`create_draft_store(None)` で DynamoDB のストアを持たせて実行し、最後に S3 クライアントを閉じる。アクセスキーは検査しない。結果は `{"is_success": true, "updated": 件数}`（batch-update）または `{"is_success": true, "processed": 件数}`（batch-create）をログに出して返す。例外はそのまま Lambda の失敗になる
- HTTP のルートは共通ルート（§4.2）を通り、`BATCH_ACCESS_KEY` を検査し、例外は 500 になる。本番の api Lambda でも公開されている
- 本番の api Lambda のイメージには Chrome が無く、pol.is のログイン情報も渡されていないので、本番で `/batch/create_all` を呼んでも投稿は成立しない。しかも失敗として最古の APPROVED の下書きの失敗回数を 1 増やす（§8.4）ので、本番では呼ばない

### 8.2 batch-update（投票情報の更新）

`update_themes()` の処理は次のとおり。

1. S3 から `csv/themes.csv` を取得し、`id` の順に並べる
2. テーマごとに、pol.is の `https://pol.is/api/v3/reportExport/<report_id>/comment-groups.csv` を httpx で取得する（`Server/web/api/utils/web_loader_httpx.py`。タイムアウトは全体 10 秒・接続 5 秒、ブラウザに似せたヘッダーを付ける）。テーマは 1 件ずつ順に処理する
3. 取得した CSV の行数を意見数、`total-votes` 列の合計を投票数とし、`themes.csv` の `votes`・`comments` と比べる
4. どちらかが変わったテーマについて、`votes`・`comments` を新しい値にし、`updated_at` を現在時刻（JST、分まで）にする。意見数が増えたときは `commented_at` も現在時刻にする。意見数が減っただけのときは `commented_at` を変えない
5. 変化したテーマが 1 件も無ければ、S3 に何も書かずに終わる（戻り値 0）
6. 変化したテーマの集計 CSV を、取得したまま `csv/report/report_<conversation_id>.csv` に書き込む
7. `themes.csv` を楽観ロックで書き換える（§9.2）。最新の `themes.csv` を読み直し、変化したテーマの行だけを `id` で上書きする

失敗時の挙動:

- どれか 1 テーマでも pol.is からの取得に失敗すると（HTTP エラーや通信エラー）、その回の処理全体が例外で終わる。取得はすべて書き込みより前に行うので、S3 には何も書かれない。次の起動（5 分後）で最初からやり直す
- `themes.csv` の書き込み競合が 3 回続いた場合も例外で終わる。このときは集計 CSV だけが先に更新されている
- Lambda の失敗は CloudWatch の Errors アラームで検知する（`docs/インフラ構成.md`）

### 8.3 batch-create（承認済み下書きの投稿）

`batch_create.handler` が呼ぶ `publish_approved_drafts(limit=1)` の処理は次のとおり。

1. 投稿状態が APPROVED の下書きを取得する。DynamoDB 実装は `id`（登録時刻）の昇順に返すので、先頭の 1 件、つまり最も古い下書きが対象になる。対象が無ければ 0 を返して終わる
2. S3 から `csv/themes.csv` を取得する
3. 下書きの `theme_comments` を `###br###` で分けて、初期コメントのリストにする
4. Selenium で pol.is 上にカンバセーションを作る（`create_theme_on_polis()`、操作の流れは下記）
5. pol.is から、作成したカンバセーションの集計 CSV を取得する
6. 新しいテーマ行を作る。`id` は `themes.csv` の最後の行の `id` に 1 を足した値、`create_date` は現在時刻（秒まで）、`created_at`・`commented_at`・`updated_at` はすべて現在時刻（分まで）。新しいテーマがどの並べ替えでも先頭に来るようにするため
7. `themes.csv` を楽観ロックで書き換え、最新の内容の末尾に新しい行を追加する（§9.2）
8. 集計 CSV を `csv/report/report_<conversation_id>.csv` に書き込む
9. 下書きに `conversation_id`・`report_id` を記録し、投稿状態を POSTED にする

**pol.is に対して行う操作**（`Server/web/api/services/batch.py` の `create_theme_on_polis()`。ブラウザ操作の部品は `Server/web/api/utils/web_loader_chrome.py` の `WebLoaderChrome`）:

1. ヘッドレスの Chrome を起動し、`https://pol.is/signin` を開く
2. 環境変数 `POLIS_LOGIN_USER`・`POLIS_LOGIN_PASSWORD` が無ければ `RuntimeError`
3. サインアウトのリンク（`#signoutLink`）が 10 秒以内に見えなければ未ログインとみなし、`#signinButton` をクリック → `#username` と `#password` に入力 → フォームを送信 → `#signoutLink` が出るまで待つ
4. 「Create new conversation」、続けて「Create Conversation」というテキストを含むボタンをクリックし、作成画面（`[data-testid^="top"]`）が出るまで待つ
5. タイトル（`[data-testid^="top"]`）と説明（`[data-testid^="description"]`）を入力し、保存ボタン（XPath 指定）をクリックする
6. 初期コメントを 1 件ずつ、入力欄（`[data-testid^="seed_form"]`）に入れて送信し、ボタンの表示が「Success!」になるのを待つ
7. 可視化のチェックボックス（`[data-testid^="vis_type"]`）をオンにする
8. 現在の URL の最後の部分を `conversation_id` とする
9. `<カンバセーションの URL>/reports` を開き、レポート作成ボタンをクリックし、表示された「Report ID: …」の文字列から `report_id` を取り出す
10. スクリーンショットを `/app/screenshot/` に保存しようとする（ローカルのコンテナ用のパス。Lambda にはこのディレクトリが無く、Selenium は書き込みに失敗すると例外を出さずに `False` を返すので、処理は続く）
11. `with` を抜けるときにブラウザを終了し、実行ごとのプロファイルディレクトリを削除する

入力には `fill_input()` を使う。ChromeDriver はキー入力で絵文字などの BMP 外の文字を打てないため、それを含む文字列は JavaScript で値を直接設定し、`input`・`change` イベントを発火させる。セレクタの多くは pol.is の画面構造に依存した XPath なので、pol.is 側の画面が変わると投稿が失敗する。

**Chrome の起動オプション**（`WebLoaderChrome._create_driver()`）:

- 常に付けるもの: `--headless=new`、`--no-sandbox`、`--disable-dev-shm-usage`、`--disable-gpu`、Safari に似せた `--user-agent`、`--window-size=1920,1080`、実行ごとに一時ディレクトリに作る `--user-data-dir`・`--disk-cache-dir`・`--data-path`
- Lambda 上（環境変数 `AWS_LAMBDA_FUNCTION_NAME` があるとき）だけ付けるもの: `--single-process`、`--no-zygote`、`--remote-debugging-pipe`、`--disable-crash-reporter`。あわせて `HOME` を `/tmp` にし、`XDG_CONFIG_HOME`・`XDG_CACHE_HOME` を `/tmp` 配下にする。Lambda は `/tmp` 以外に書き込めず、プロセスの作り方にも制約があるため、これが無いと Chrome が起動直後に終了する
- プロファイルを実行ごとの一意のディレクトリにしているのは、固定のパスだと、タイムアウトで強制終了したときに残るロックファイルが、同じコンテナを再利用する次回以降の起動をすべて失敗させるため
- ChromeDriver は `/usr/bin/chromedriver` を固定で使う。ページ読み込みのタイムアウトは 30 秒

**成功時と失敗時の更新**:

| 起きたこと | 下書き | `themes.csv`・集計 CSV | Lambda の結果 |
| --- | --- | --- | --- |
| 成功 | POSTED、`conversation_id`・`report_id` を記録 | 新しい行を追加、集計 CSV を作成 | 成功（`processed: 1`） |
| pol.is 上の作成（手順 4〜6）で例外 | `publish_retry_count` を 1 増やす。上限に達したら FAILED（§8.4） | 変更なし | 失敗（例外をそのまま送出） |
| CSV・S3・ストアの更新（手順 7〜9）で例外 | 変更なし（失敗回数にも数えない） | 途中まで書かれていることがある | 失敗 |

最後の行の場合、pol.is 上にはカンバセーションが作られたまま下書きが APPROVED に残るので、次の起動で同じ下書きがもう一度 pol.is に作られる。インフラ側の失敗を下書きの失敗回数に数えないのは、下書きの内容に問題が無いのに隔離しないためである。

### 8.4 投稿失敗のリトライと隔離

- 下書きの投稿に失敗するたびに `publish_retry_count` を 1 増やし、9 回連続で失敗した下書きを FAILED（102）に隔離する。上限は `Server/web/api/configs/constants.py` の `PUBLISH_RETRY_LIMIT`。隔離すると次の起動からは後ろの APPROVED の下書きが処理されるので、1 件の壊れた下書きが後続をずっと塞ぐことがない
- 回数を記録する前に `rollback()` を呼ぶ。MySQL では、先に処理した下書きの未確定の変更が記録のコミットに巻き込まれないようにするため（DynamoDB では何もしない）
- 記録そのものに失敗しても、ログに残すだけで、元の例外を隠さない
- 上限が 9 の理由（`Server/web/api/configs/constants.py` のコメントによる）: Scheduler 側の再試行は 0 回だが、Lambda の非同期呼び出しの既定の再試行（2 回）が働くため、実測で 15 分の 1 サイクルあたり 3 回試行される。9 回はおよそ 3 サイクル、30 分強に当たり、pol.is 側の 30 分未満の一時的な障害では健全な下書きを隔離しない
- FAILED の下書きは、管理画面で承認し直す（`/admin/approve`）と APPROVED に戻り、`publish_retry_count` が 0 に戻って再び投稿の対象になる

### 8.5 滞留監視とリマインド（`Server/web/api/lambda_handlers/backlog_monitor.py`）

batch-create のハンドラは、成功しても失敗しても最後に `backlog_monitor.report()` を呼ぶ。

- **メトリクス**: FAILED の件数・APPROVED の件数・今回投稿できた件数（失敗時は 0）を数え、Embedded Metric Format（EMF）の JSON を 1 行、標準出力に書く。名前空間は `PolisJAPAN/Batch`、ディメンションは `FunctionName`（値は `polisjapan-batch-create`）、メトリクス名は `FailedDrafts`・`PendingDrafts`・`PublishedDrafts`。CloudWatch Logs が自動でメトリクスとして取り出すので、`PutMetricData` の API も IAM 権限も要らない。`Logger` は色コードを付けるので、この行だけは `print` で出す。このメトリクスを使うアラームの定義は `docs/インフラ構成.md`
- **毎朝のリマインド**: FAILED が 1 件以上あり、環境変数 `ALERTS_TOPIC_ARN` があり、起動時刻が JST 9:00〜9:14 のとき、SNS にメッセージを送る。スケジュールが 15 分間隔なので、この枠に入る起動は 1 日 1 回になる。判定には処理の終了時刻ではなく起動時刻を使う。件名は「[PolisJAPAN] 投稿失敗の下書きがN件残っています」、本文には FAILED のテーマ名（最大 20 件、超えた分は件数のみ）と対応手順（CloudWatch Logs で原因を確認し、管理画面で再承認または却下する）を書く
- **監視自体の失敗**: 例外はログに残して握りつぶし、投稿の処理結果を変えない。メトリクスが途絶えたことは、報告が途絶えたことを検知するアラームで分かる
- 件数で監視するのは、隔離のあとは batch-create が「処理 0 件で正常終了」になり、Lambda の Errors のアラームがすぐ OK に戻ってしまうため。件数のアラームは滞留が解消するまで ALARM のままになる

## 9. S3・CloudFront へのアクセス

### 9.1 ストレージのユーティリティ（`Server/web/api/utils/storage_s3.py`）

`StorageS3` は aioboto3 の非同期クライアントを包んだクラスで、`open()` と `close()` を明示的に呼んで使う。API ではリクエストごとに共通ルートが開閉し、Lambda ハンドラでは開始時に開いて `finally` で閉じる。

| メソッド | 内容 |
| --- | --- |
| `exists` | `head_object` で存在確認。404 なら `False` |
| `get_bytes` | オブジェクトの取得 |
| `get_bytes_and_etag` | オブジェクトと ETag の取得（楽観ロック用） |
| `upload_bytes` | `put_object`。`content_type`・`cache_control`・`if_match` を指定できる |
| `delete_object` | 削除 |
| `create_invalidation` | CloudFront の指定パスのキャッシュ無効化 |

- 接続タイムアウト 5 秒、読み取りタイムアウト 30 秒、botocore の standard モードで最大 5 回の再試行
- S3 の例外は `StorageS3Error` に、`If-Match` の不一致（412・`PreconditionFailed`）は派生の `StorageS3PreconditionError` に包んで投げる
- バケットは環境変数 `CSV_BUCKET`（未設定なら本番の `app.pol-is.jp`）。E2E テスト用のサンドボックスのバケットに差し替えるためにこの変数がある
- `put_object` の引数を作る部分は純関数 `build_put_args()` に分けてあり、テストで検証している

### 9.2 `themes.csv` の楽観ロック

`themes.csv` は batch-update（5 分ごと）と batch-create（15 分ごと）の両方が「読む → 直す → 書く」で更新する。単純に上書きすると、片方が追加した行をもう片方が消すことがあるので、`BatchService.write_themes_csv(mutate)` で書く。

1. `get_bytes_and_etag()` で最新の内容と ETag を取る
2. 内容を解析し、`mutate`（変更を加える関数）を適用する
3. 取得した ETag を `If-Match` に付けて書き込む
4. その間に他方が書き込んでいて 412 になったら、1 に戻って最新を読み直す。3 回続けて競合したら `StorageS3Error` を投げる

`mutate` は競合のたびに最新の内容に対してかけ直されるので、何度適用しても同じ結果になる処理（batch-update は `id` での上書き、batch-create は新しい行の追加）でなければならない。

`/batch/delete` だけは楽観ロックを使わず、`themes.csv` を読んで該当行を除き、そのまま上書きする。

### 9.3 キャッシュの扱い

- CSV を書くときは必ず `Cache-Control: max-age=300` を付ける（`Server/web/api/services/batch.py` の `CSV_CACHE_CONTROL`）。CloudFront はこれを TTL として使うので、更新は最大 5 分で配信に反映される。CloudFront 側のキャッシュポリシーとクライアント側の `?_v=` の付け方は `docs/インフラ構成.md` と `docs/クライアント設計.md`
- 通常の更新ではキャッシュの無効化を行わない
- `/batch/delete` だけは、削除したオブジェクトに Cache-Control が付かず TTL で消えないため、環境変数 `CLOUDFRONT_DISTRIBUTION` が設定されていれば、`/csv/report/report_<conversation_id>.csv` と `/csv/themes.csv` の 2 パスに限って無効化する。無効化の権限を持つのは api Lambda だけである

| 項目 | `Server/web/Dockerfile` | `Server/web/Dockerfile.lambda` | `Server/web/Dockerfile.lambda-chromium` |

| その他 | ビルド時に pip-licenses で `THIRD_PARTY_LICENSES.html` を作る | | ビルドの最後に `chrome --version` と `chromedriver --version` が固定バージョンと一致するかを確かめ、違えばビルドを失敗させる |

- ローカルのイメージはビルドのたびにロックを作り直すので、入る依存の版が `Server/web/poetry.lock` と一致する保証は無い。本番の 2 つのイメージはロックファイルどおりに入る
- ローカルの `Server/web/Dockerfile` は `COPY . .` のあとに `THIRD_PARTY_LICENSES.html` をビルドコンテキストから再度 `COPY` している。このファイルは gitignore されており、clone した直後には存在しないので、その状態でビルドが通るかは未確認
- Lambda のイメージを Python 3.12 にしているのは、3.11 の Lambda ベースイメージが Amazon Linux 2（glibc 2.26）で、numpy 2.x などの manylinux_2_28 の wheel が使えず、ソースからのビルドになるため
- Lambda はマルチプラットフォームのマニフェストを扱えないので、CI（`.github/workflows/deploy-server.yml`）は `linux/amd64` だけを、provenance と SBOM を無効にしてビルドする
- `Server/web/api/utils/web_loader_chrome.py` は `/usr/bin/chromedriver` を固定で参照するので、batch-create のイメージは Chrome for Testing の `chrome` と `chromedriver` を `/opt/` に展開し、`/usr/bin/google-chrome` と `/usr/bin/chromedriver` にシンボリックリンクを張っている

**Chrome のバージョンを固定している理由**: batch-create のイメージは Chrome for Testing の `150.0.7871.115` を `ARG CHROME_VERSION` で固定している。固定しないと、イメージを作り直すたびにその時点の最新版の Chrome が入り、Lambda 上で起動できなくなることがある（`SessionNotCreatedException: Chrome instance exited`。この状態では投稿がすべて失敗する）。この不具合は Lambda のローカルエミュレータ（RIE）では再現しないので、バージョンを上げるときは実際の Lambda で投稿が通ることを確かめてから値を変える。手順は `docs/運用手順書.md`。

**デプロイ**: `main` ブランチで `Server/web/` 以下が変わると、`.github/workflows/deploy-server.yml` が 2 つのイメージをビルドして ECR に push し、3 つの Lambda のイメージを切り替え、`https://api.pol-is.jp/batch/healthcheck` を最大 10 回確認する。`Server/lambda/` の変更はこのワークフローの対象外である。

## 11. お問い合わせ Lambda（`Server/lambda/contact/`）

LP とアプリ内のお問い合わせフォームの送信先。API Gateway（REST）経由で `https://contact.pol-is.jp/contact` への POST を受け、Amazon SES でメールを 2 通送る。API の入出力は `docs/API仕様.md`、リソースの設定は `docs/インフラ構成.md`。

`Server/lambda/contact/lambda_function.py` の `lambda_handler` の処理は次のとおり。

1. イベントに `body` があれば JSON として解析し、無ければイベント自体を入力とみなす（コンソールからの直接テスト用）
2. `mail`・`name`・`content` を取り出す（無ければ空文字）。入力の検証は行わない
3. 受け取った内容を `print` でログに出す（CloudWatch Logs に送信者の氏名・メールアドレス・本文が残る）
4. 運営宛てに「【お問い合わせ】Webフォームからの新規問い合わせ」を送る。送信元と運営の宛先はコードに直接書かれている
5. 入力されたメールアドレス宛てに自動返信を送る
6. 200 と `{"message": "ok", "ses_message_id": <自動返信のメッセージ ID>}` を返す

- SES やその他の例外では 500 と `{"message": "send error" または "internal error", "error": <例外の文字列>}` を返す。運営宛てを送ったあとで自動返信に失敗すると、運営宛ての 1 通だけが送られた状態で 500 になる
- すべてのレスポンスに `Access-Control-Allow-Origin: *` を付ける。Lambda プロキシ統合ではプリフライトとは別に実際のレスポンスにも必要で、無いとブラウザが結果を読めない
- SES のクライアントは環境変数 `AWS_REGION`（Lambda が自動で設定する）のリージョンを使う
- デプロイは手動（zip にして `aws lambda update-function-code`）。手順は `Server/lambda/contact/README.md`。Terraform は関数の設定だけを管理し、コードは管理しない
- 疎通確認は不正な JSON の本文を送ると例外の経路に入り、メールが送られない
- 共有（OGP）用の Lambda のコードはこのリポジトリに無い（Terraform は関数の設定だけを管理している）
