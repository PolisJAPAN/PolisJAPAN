## 1. サービス概要

### 1.1 背景

Polis は「ブロードリスニング」（インターネット経由で意見を募り、テクノロジーを活用して合意形成を探る取り組み）を実現するSNSシステムである。

- 「賛成」「反対」の投票を通じ、レスバトルや誹謗中傷の応酬を生まない議論ができる
- 統計的分析による意見グループの可視化で「落とし所」となる意見を探ることができる

一方、オリジナルの Polis は日本のユーザーにとってユーザービリティが低く、そのままでは日本での普及が難しい。

### 1.2 目的

**「Polis」のシステムを日本に社会実装する。**

そのために、下記の課題を解決し、Polis をコアとして SNS に求められる周辺機能を実装する。

1. 日本語による UI・操作説明がなく、日本人ユーザーが初見で受け入れ難い
2. PC 前提の UI となっており、モバイルユーザーが快適に使用できない
3. 一覧・検索機能がなくテーマを見つけることができない
4. 投稿に手間が掛かり、思いついたテーマを議題にするまでのハードルが高い

### 1.3 実装方針

投票・意見グループ化などのコア機能は本家 Polis（pol.is）をそのまま利用し、本システムは以下を提供する。

- LP によるサービス周知
- 日本語 UI・チュートリアル
- テーマ一覧・検索機能
- モバイル最適化された体験（PWA 対応）
- AI アシストによる簡易なテーマ作成
- Polis の投票データを取得・集計して独自表示する分析画面

## 3. システム構成

### 3.1 ドメイン構成

| ドメイン | 役割 | ホスティング |
| --- | --- | --- |
| `pol-is.jp` | LP | S3（バケット `pol-is.jp`）+ CloudFront |
| `app.pol-is.jp` | WEB アプリ（PWA） | S3（バケット `app.pol-is.jp`）+ CloudFront |
| `api.pol-is.jp` | API（テーマ作成・バッチ・管理） | API Gateway (HTTP API) + Lambda（コンテナ、FastAPI + Mangum）。TLS は ACM（自動更新） |
| `admin.pol-is.jp` | 管理画面 | S3 + CloudFront + CloudFront Function（IP 許可リスト検査） |
| `contact.pol-is.jp` | お問い合わせ受付 | API Gateway (REST) + Lambda `PolisJAPAN-Contact` + SES（**us-east-1**） |
| `share.pol-is.jp` | 共有リンク（OGP 付きリダイレクト） | CloudFront + API Gateway (REST) + Lambda `PolisJAPAN-GetOGP`（**us-east-1**）。Lambda のコードはリポジトリ外 |
| `pol.is` | 投票・意見グループ化のコア機能（本家 Polis） | 外部サービス |

AWS リージョン: `ap-northeast-3`（大阪）。ただし contact / share の Lambda・API Gateway と、Route53 ヘルスチェック用のアラームは `us-east-1`

### 3.2 アーキテクチャ概要

**フルサーバーレス構成**（2026-07 移行完了）。常時稼働サーバーを持たず、コストメリットと可用性を両立する。

```
ユーザー
  │
  ├─ Route 53 → CloudFront → S3 ……… LP / WEBアプリ（静的サイト・CSVキャッシュ）
  │     └─ csv/*: バッチLambdaが Cache-Control: max-age=300 付きで直接更新
  │
  ├─ API Gateway → Lambda → SES …… お問い合わせ通知送信（contact）
  ├─ CloudFront → API Gateway → Lambda … 共有リンク（share）
  │
  ├─ pol.is（埋め込みAPI）………………… 投票・意見投稿・意見グループ化
  │
  ├─ admin.pol-is.jp ………………………… S3 + CloudFront + CloudFront Function（IP制限）
  │
  └─ api.pol-is.jp …… API Gateway (HTTP API) + ACM
        │
        ├─ Lambda「api」(コンテナ, FastAPI + Mangum)
        │     /theme/*（AIテーマ生成・下書き投稿）・/admin/*（下書き管理）・/batch/*（healthcheck・手動バッチ・削除）
        │
        ├─ Lambda「batch-update」← EventBridge Scheduler rate(5 minutes)
        │     pol.is レポートCSV取得 → S3更新（Cache-Control付与）
        │
        └─ Lambda「batch-create」(コンテナ, Selenium + headless Chromium)
              ← EventBridge Scheduler rate(15 minutes)
              APPROVED下書きを pol.is に作成（1起動1件）→ themes.csv 追記
              連続9回失敗した下書きは FAILED に隔離（後続を塞がない）

データ層
  ├─ DynamoDB「polisjapan-drafts」……… テーマ下書き（旧 MySQL t_draft の移行先）
  ├─ S3 app.pol-is.jp ……………………… テーマ/レポートCSV
  ├─ S3 polisjapan-archive ……………… 旧環境のMySQL全ダンプ等のアーカイブ
  └─ SSM Parameter Store (SecureString) … 全シークレットの一元管理

監視
  ├─ Route53ヘルスチェック（/batch/healthcheck）→ CloudWatchアラーム → SNS → メール
  ├─ api / batch-update / batch-create の Errors メトリクスアラーム
  └─ 投稿滞留の監視（FAILED 件数・投稿停滞・報告途絶のアラーム + 毎朝のリマインド、§7.1）
```

- テーマ・投票データの実体は **S3 上の CSV ファイル**（クライアントが直接読む読み取り専用「データベース」）
- テーマ下書きは **DynamoDB**（`polisjapan-drafts`、オンデマンド課金・PITR有効）。旧ユーザーアカウント機能（休眠）はデータごと S3 アーカイブへ退避し移行対象外
- インフラ全体を **Terraform**（`Infra/terraform/`）でコード管理（既存リソースも import 済み・計 125 リソース、2026-11-12 時点）

## 4. クライアント仕様（`Client/`）

3 つの静的サイトで構成され、開発時はそれぞれ独立した nginx コンテナで配信される（`Client/docker-compose.yml`）。

| サイト | ディレクトリ | 開発ポート | 本番 |
| --- | --- | --- | --- |
| LP | `Client/public_html/` | 8080 | s3://pol-is.jp/ |
| WEB アプリ | `Client/public_html_app/` | 8081 | s3://app.pol-is.jp/ |
| 管理画面 | `Client/public_html_admin/` | 8082 | admin.pol-is.jp（S3 + CloudFront、IP 制限） |

### 4.1 LP（`public_html/`）

- `index.html` — タイトル「Polis JAPAN | 分断をなくすSNS」。セクション: `#hero` / `#problems` / `#features` / `#demo`（デモテーマカード → アプリへ誘導）/ `#info`。JSON-LD 構造化データを含む
- サブページ: `private/`（プライベート版について。本家 pol.is で URL 限定の議題を作る手順）、`contact/`（お問い合わせ）、`terms/`（利用規約）、`policy/`（プライバシーポリシー）、`license/`（ライセンス）
- `javascript/contact.js` — お問い合わせフォーム。`https://contact.pol-is.jp/contact` へ `mail` / `name` / `content` を JSON で POST。入力バリデーションは無く、送信結果を待たずに完了画面へ切り替える（失敗しても完了表示になる）
- Google Search Console 検証ファイルを配置

### 4.2 WEB アプリ（`public_html_app/`）

PWA として登録可能（`manifest.json`、`javascript/service-worker.js`、スプラッシュ画像一式は `Asset/PWA/generate.zsh` で生成）。

#### 画面構成

| 画面 | ファイル | 概要 |
| --- | --- | --- |
| ホーム（テーマ一覧） | `index.html` + `javascript/home.js` | テーマカードの一覧表示・検索・絞り込み・ソート |
| テーマ詳細・分析 | `detail/index.html` + `javascript/detail.js` | Polis 埋め込みによる投票と、独自レンダリングの分析レポートのタブ切替 |
| テーマ作成モーダル | `javascript/create.js` | AI アシスト／手動の 2 モードによるステップ式作成ウィザード |

#### ホーム画面（`home.js`）

- `/csv/themes.csv` を取得しテーマカードを描画
- カテゴリ絞り込み（0: 全て（初期値）、fav: お気に入り、1: 社会・政治、2: お金・資産、3: 男女・性別、4: 外国人問題、5: テクノロジー、6: 医療・福祉、7: 生活、8: その他）。選択中のタブを再度押すと「全て」に戻る
- お気に入り（`javascript/favorites.js`）: カードの☆と詳細画面の★で登録。保存先はブラウザの localStorage `favorite_conversations` のみ（サーバーには送らない）。初回追加時は注意ダイアログ、2 回目以降はトースト
- キーワード検索（空白区切りの AND 検索・ローカル検索）。`data-searchtext` の索引化は現状実行されておらず、カードの表示テキスト全体（「更新」「意見」「投票」の文言や件数を含む）が検索対象になっている
- ソート: 更新順（デフォルト、`updated_at` 降順）・意見順（`commented_at` 降順）・新着順（ID降順）・古い順（ID昇順）・人気順（投票数）。ソートボタンは選択中のソート名を表示
- テーマカード右上に更新日時（`updated_at`）を表示（旧データ等で空白の場合は非表示）
- ボトムメニューにハンバーガーメニュー（お知らせ・改善要望・プライベート版について・お問い合わせ・利用規約・プライバシーポリシー）。「改善要望」は実テーマ `/detail/?conversation_id=9knucbecnr` へ遷移する
- お知らせ（`javascript/notice.js`）: スライドモーダル+アコーディオン表示。`NOTICES` 配列が一覧の源で、本文は `notice/*.html` を取得。未読があれば自動表示（Cookie `notice_last_seen_id` で既読管理、チュートリアル表示中は閉じるまで待つ）
- お問い合わせ（`javascript/contact.js`）: アプリ内モーダル（入力 → 確認 → 完了）。メール（`@` を含む）と内容が必須。下書きは localStorage `contact_draft`
- チュートリアル: オプトアウト（Cookie `tutorial_optout`）するまで、1 日 1 回（午前 4 時区切り）自動表示

#### テーマ詳細画面（`detail.js`）

- URL クエリ `?conversation_id=` を `.polis` 要素の `data-conversation_id` に設定し、`https://pol.is/embed.js` を動的ロードして投票 UI を埋め込む
- 分析レポートは iframe ではなく独自実装:
  `/csv/report/report_<conversation_id>.csv` を取得し、コメントごとの賛成・反対・パスの円グラフと意見グループ別ツールチップを描画（賛成率順ソート、円グラフタップで意見内容・投票数を表示）
- 共有ボタン: `https://share.pol-is.jp/link?conversation_id=...` を生成しクリップボードへコピー
- 「詳細レポート」ボタン: 本家 `https://pol.is/report/<report_id>` へリンク

#### テーマ作成（`create.js`）

- **AIアシストモード**: テーマ入力 → 対立軸生成（`/theme/generate_axis`）→ シードコメント生成（`/theme/generate_comments`）→ 説明文生成（`/theme/generate_descriptions`）→ カテゴリ選択 → 投稿（`/theme/post_draft`）
- **手動モード**: テーマ・コメント・説明・カテゴリを手入力して投稿（対立軸の入力は無い）。コメント欄は 15 個あり、現状は 15 個すべての入力が必須（画面の文言は「8個の意見が必要です」のままで食い違っている）
- 文字数上限: タイトル 80 文字・説明 200 文字（カウンター表示、`maxlength`、「次へ」押下時の検査、サーバー側の検査）
- 下書きは localStorage に自動保存（キー `<AI_ASSIST|MANUAL>_CREATE_DRAFT_<THEME|AXIS|COMMENTS|DESCRIPTION|CATEGORY>`。投稿成功時のみ削除）
- 投稿された下書きは DynamoDB `polisjapan-drafts` に **APPROVED（承認済）で直接登録**され、管理者の操作を経ずに batch-create（15 分間隔）が Polis へ公開する（§6 参照）。審査を挟まずに公開するのは現行の仕様である（2026-11-11 確認）。画面の文言「審査通過後に公開」は、この仕様に合わせた更新がされていない

#### 共通ライブラリ（`common.js`）

- `API_URL = "https://api.pol-is.jp/"`、`USER_ACCESS_KEY`（bot 対策用アクセスキー）
- CSV パーサ（`loadCsvAsJson` / `parseCSV`）、Cookie・localStorage ヘルパー、`TutorialManager`（チュートリアル）、`ModalManager`、`CustomSelectManager`、クリップボード、ローディング表示

### 4.3 管理画面（`public_html_admin/`、配信コピーは `Server/admin/`）

- 本番は `admin.pol-is.jp`（S3 非公開バケット + OAC + CloudFront）で配信。CloudFront Function が viewer IP を許可リストと照合し、不一致は 403（旧 EC2 nginx の `/dashboard/` IP 制限を代替）
- IPv6 からのアクセスは常に 403
- 運営者がアクセスキーを入力（Cookie `admin_access_key`、30 日）し、`https://api.pol-is.jp/admin/info` からテーマ下書き一覧（論理削除されていない全件。投稿済も含む）を取得
- 下書きの承認（`/admin/approve`）・編集（`/admin/edit`）・削除（`/batch/delete`。確認ダイアログなし）を実施。却下の機能は無い
- 投稿失敗で隔離された下書き（FAILED）には「投稿失敗」タグを表示し、承認ボタンで再投稿できる（リトライ回数は 0 に戻る）
- 「生成」ボタン（`/batch/generate`）は API 側が未マウントのため機能しない。変換欄下の「更新」ボタン（`/batch/create_all`）は本番の api Lambda に Chrome が無いため成立しない（失敗しつつ最古の APPROVED 下書きのリトライ回数を加算するため、押さないこと）

### 4.4 スタイル（`Client/scss/`）

- 単一エントリ `style.scss` → 各サイトの `style.css` に sass コンテナ（node:20-alpine、`sass --watch`）でコンパイル
- 構成: `common/`（reset / color / font / components / layout / animation）、`pages/top/`（LP）、`pages/home/`、`pages/detail/`、`pages/admin/`
- パーシャルは `_` プレフィックスの命名規則

## 5. サーバー仕様（`Server/web/api/`）

### 5.1 技術スタック

| 項目 | 内容 |
| --- | --- |
| フレームワーク | FastAPI（async）。ローカルは uvicorn、本番 Lambda は **Mangum** ハンドラ（`main.py` の `handler = Mangum(app)`） |
| 言語 / パッケージ管理 | Python 3.11（ローカル開発）/ 3.12（Lambda コンテナ）/ Poetry |
| データ層 | **DynamoDB**（本番）/ MySQL 8.0 + SQLAlchemy 2.0（ローカル開発）。`repositories/draft.py` の DraftStore 抽象で `DATA_BACKEND`（mysql / dynamodb）を切り替え |
| AI 連携 | LangChain + langchain-openai（OpenAI GPT-5 系）、LangSmith（プロンプト管理・トレーシング）、LangGraph |
| スクレイピング | Selenium（Chromium）+ BeautifulSoup、httpx |
| Web 検索 | DuckDuckGo（ddgs） |
| AWS 連携 | aioboto3 / boto3（S3・DynamoDB） |

`main.py` は `APP_ENV` が `production` または `serverless`（本番 Lambda）のとき `/docs` `/redoc` `/openapi.json` を無効化する（2026-11-11 に `serverless` を対象へ追加。それまで本番で公開されていた）。また`TimeoutMiddleware`（300 秒）と CORS を設定。マウントされるルーターは `admin` / `batch` / `theme` の 3 つ（`user` ルーターは実装済みだが未マウントの休眠機能）。アプリの memcached 依存は移行時に削除済み（ローカルの docker-compose に cache サービス定義のみ残置）。

リクエストは `core/common_route.py`（`CommonRoute`）で共通処理される: パスからルーター/API 名を解決 → 認証チェック → 非同期 DB セッション開始（MySQL バックエンド時のみ）→ サービスの動的生成（`api.services.<router>`）→ S3 クライアント初期化 → ハンドラ実行 → 後処理。エラーは `trace_id` 付き JSON に正規化される。

### 5.2 API エンドポイント一覧

#### `/theme`（テーマ作成 API・`generate_*` は `USER_ACCESS_KEY` で保護）

| エンドポイント | メソッド | 概要 |
| --- | --- | --- |
| `/theme/generate_axis` | POST | テーマから対立軸（立場）を AI 生成 |
| `/theme/generate_comments` | POST | 対立軸ごとのシードコメントを AI 生成 |
| `/theme/generate_descriptions` | POST | テーマ説明文を AI 生成 |
| `/theme/post_draft` | POST | ユーザー投稿の下書きを DynamoDB に登録（post_status: APPROVED）。タイトル 80・説明 200 文字まで。**アクセスキーは照合していない**（形式チェックのみ）ため、呼べば必ず登録され、約 15 分以内に pol.is へ公開される |

#### `/batch`（バッチ API・`BATCH_ACCESS_KEY` で保護）

| エンドポイント | メソッド | 概要 |
| --- | --- | --- |
| `/batch/update` | POST | 全テーマの最新レポート CSV を pol.is から取得し、投票数・コメント数に変化があれば S3 の `themes.csv` / レポート CSV を `Cache-Control: max-age=300` 付きで更新（CloudFront 無効化は廃止し TTL で反映） |
| `/batch/create_all` | POST | APPROVED の下書きを Selenium で pol.is 上に作成し、`themes.csv` に追加、POSTED に更新（件数無制限）。本番の api Lambda には Chrome と pol.is 認証情報が無く成立しない（ローカル用） |
| `/batch/delete` | POST | 入力は `t_draft_id`。テーマを `themes.csv` から削除、レポート CSV を S3 から削除、下書きを論理削除（削除は TTL で反映できないため対象パス限定の CloudFront 無効化を実施）。pol.is 上のカンバセーションは削除しない |
| `/batch/healthcheck` | GET | 死活監視（Route53 ヘルスチェックの監視先） |

本番の定期実行は HTTP 経由ではなく、EventBridge Scheduler が専用 Lambda（`lambda_handlers/batch_update.py` / `batch_create.py`）を直接起動する（§7 参照）。HTTP の `/batch/*` はローカル開発・手動実行用として残るが、本番でも公開されており、`BATCH_ACCESS_KEY` があれば実行できる（IP 制限は無い）。管理画面の削除もこの経路を使う。

#### `/admin`（管理 API・`BATCH_ACCESS_KEY` + IP 許可リストで保護）

| エンドポイント | メソッド | 概要 |
| --- | --- | --- |
| `/admin/info` | POST | 下書き一覧取得（DynamoDB Scan、論理削除されていない全件） |
| `/admin/approve` | POST | 下書きを APPROVED に更新し、リトライ回数を 0 に戻す（現在の状態は確認しない） |
| `/admin/edit` | POST | 下書き内容の編集 |

#### `/user`（未マウント・休眠機能）

`mail_check` / `create` / `login`（httponly の `session_id` Cookie を発行）/ `reload` / `edit` / `delete`。パスワードは `utils/security.py` でハッシュ化。

エラーはカスタムステータスコードを使用する: 481 アクセスキー不正（全 API 共通）／482 は API により意味が異なる（`/admin/*` は IP アドレス不正、`/batch/delete` は下書きが見つからない）／483 `/admin/approve`・`/admin/edit` の下書きが見つからない。想定外の例外と入力検証エラーは 500（`{"message","trace_id"}`）になる。`/admin/*` はアクセスキー → IP の順に検査する。

### 5.3 AI テーマ生成（`services/theme.py`）

- モデル: API から呼ばれる対立軸・コメント・説明の生成はすべて `gpt-5-nano`（reasoning_effort=low）。`gpt-5` は現在呼び出し元の無い旧パイプラインでのみ使用

- LangChain LCEL（`RunnableParallel` / `RunnableBranch` / `.abatch`）でチェーン構成

### 5.4 テーマ自動作成（`services/batch.py`）

- Twitter / Togetter のスクレイピング（Selenium + BeautifulSoup）によるテーマ候補の自動抽出パイプラインのコードを持つが、現在は呼び出し元が無い（`/batch/generate` は未マウント）

### 6.2 テーマ下書き — DynamoDB「polisjapan-drafts」

本番のテーマ下書きは DynamoDB で管理する（旧 MySQL `t_draft` から 2026-07 に移行）。オンデマンド課金・PITR 有効。

| 属性 | 型 | 備考 |
| --- | --- | --- |
| `id` (PK) | N | 旧 `t_draft.id` を踏襲。新規作成分は epoch 秒ベース ID |
| `post_status` | N | 0=SUGGESTED / 1=GENERATED / 2=APPROVED / 3=POSTED / 101=REJECTED / 102=FAILED（`models/types.py::PostStatus`）。現行コードが設定するのは 2・3・102 のみ |
| `publish_retry_count` | N | batch-create の連続失敗回数。`PUBLISH_RETRY_LIMIT`（9）に達すると FAILED に隔離。再承認で 0 に戻る |
| `title`, `theme_name`, `theme_description`, `theme_comments`, `theme_category`, `conversation_id`, `report_id`, `origin_url` | S/N | 旧カラム踏襲 |
| `status`, `create_date`, `update_date` | N/S | 論理削除フラグと日時（ISO 8601 文字列） |

- GSI: `post_status-index` — batch-create の「APPROVED 一覧取得」と滞留監視の件数取得に使用（admin の一覧表示は Scan）
- アクセスは `repositories/draft_store_dynamo.py`（DraftStore 抽象の DynamoDB 実装）経由

ローカル開発では従来の MySQL（`app_db`、`models/tables.py`）を使用（`DATA_BACKEND = "mysql"`）。休眠機能のテーブル（`t_user` / `t_account` / `t_user_add`）は移行せず、全データを S3 `polisjapan-archive` にアーカイブ済み。

### 6.3 投票情報自動更新のデータフロー

1. EventBridge Scheduler が 5 分間隔で Lambda「batch-update」を起動
2. S3 から `csv/themes.csv` をダウンロード
3. 各テーマの `https://pol.is/api/v3/reportExport/<report_id>/comment-groups.csv` を httpx で取得
4. 投票数・コメント数に変化があれば、レポート CSV と再生成した `themes.csv` を `Cache-Control: max-age=300` 付きで S3 にアップロード（`themes.csv` は ETag If-Match の楽観ロックで batch-create との書き込み競合を防止）
5. クライアントは CloudFront 経由で最新 CSV を直接取得（TTL 5 分で自動反映。無効化 API は使わない）

補足: 投票数または意見数が変わったテーマは `updated_at` を、意見数が増えたテーマは `commented_at` も更新する。1 テーマでも pol.is からの取得に失敗すると、その回は全体を中断して何も書き込まない（次回実行で再試行）。

## 7. バッチ（EventBridge Scheduler + Lambda）

本番の定期実行は EventBridge Scheduler が専用 Lambda を直接起動する（`Infra/terraform/modules/batch/`）。

| ジョブ | スケジュール | Lambda | 内容 |
| --- | --- | --- | --- |
| batch-update | rate(5 minutes) | `lambda_handlers/batch_update.py`（api と同一コンテナイメージ・ハンドラ指定のみ変更） | 投票情報の取得・CSV 更新（§6.3） |
| batch-create | rate(15 minutes) | `lambda_handlers/batch_create.py`（Selenium + headless Chromium 入りコンテナ、メモリ 2048MB・タイムアウト 900 秒） | 承認済み下書きの Polis への公開。**1 回の起動で 1 件だけ処理**し、15 分制限内に確実に収め失敗の影響を 1 件に限定（残りは次回実行で処理） |

- api・両バッチ Lambda の Errors メトリクスにアラームを設定し、SNS 経由でメール通知（旧環境には無かったバッチ失敗検知）
- batch-create は同時実行数 1。Scheduler 側の再試行は 0 回だが、Lambda の非同期呼び出しの再試行により 1 サイクルあたり最大 3 回試行される
- バッチ処理量は管理テーマ数に比例し、ユーザーアクセスに依存して急増減しないため、Lambda の従量課金と相性が良い
- 旧 cron コンテナ（`Server/cron/`）は旧 EC2 専用だったため削除済み（2026-07-07）。ローカルでバッチを動かす場合は `/batch/update` 等を手動で curl する

### 7.1 投稿失敗の隔離と滞留監視

- **隔離**: batch-create は pol.is への作成に失敗すると `publish_retry_count` を加算し、9 回連続で失敗した下書きを FAILED（102）に隔離する。隔離後は後続の下書きが処理される。FAILED の下書きは、管理画面の「承認」で APPROVED に戻すと再投稿される
- **メトリクス**: batch-create は起動のたびに、名前空間 `PolisJAPAN/Batch` へ `FailedDrafts`（FAILED 件数）・`PendingDrafts`（APPROVED 件数）・`PublishedDrafts`（今回投稿できた件数）を出力する（`lambda_handlers/backlog_monitor.py`、Embedded Metric Format）
- **アラーム**（`Infra/terraform/modules/monitoring/`、通知先は SNS `polisjapan-alerts`）

| アラーム | 条件 |
| --- | --- |
| `polisjapan-batch-create-failed-drafts` | FAILED の下書きが 1 件以上残っている間 ALARM |
| `polisjapan-batch-create-stalled` | 投稿待ちがあるのに 2 時間 1 件も投稿できていない |
| `polisjapan-batch-create-no-report` | batch-create からの報告が 1 時間途絶えた |

- **リマインド**: FAILED が残っている間、毎朝 9 時台（JST）にタイトル一覧つきのメールを送る
- **背景**: 2026-10-16 の再ビルドで Chrome が 150→155 に上がり Lambda 上で起動不能になった。失敗した下書きが隔離されると「処理 0 件で正常終了」になり Errors アラームがすぐ OK に戻るため、約 4 週間・45 件の滞留に気づけなかった。再発防止として件数ベースの監視を追加した（2026-11-11）

## 8. インフラ・デプロイ

### 8.1 本番構成（フルサーバーレス・Terraform 管理）

- **静的サイト**: S3 + CloudFront（LP: CF `E1L9GH70CTWAY6` / アプリ: CF `E1VDGUET2Z2OBX` / 管理: admin.pol-is.jp）、Route 53 で DNS 管理
- **API**: API Gateway (HTTP API) + Lambda ×3（api / batch-update / batch-create、§3.2）。コンテナイメージは ECR（`polisjapan-api` / `polisjapan-batch-create`）
- **TLS**: ACM（自動更新）。旧 Let's Encrypt / certbot 運用は廃止
- **シークレット**: SSM Parameter Store (SecureString) で一元管理し、Terraform が Lambda 環境変数へ注入
- **AWS 認証**: Lambda は IAM ロール、ローカルは環境変数のアクセスキー
- **IaC**: `Infra/terraform/`（modules: data / api / batch / admin-site / monitoring）。tfstate は `s3://polisjapan-tfstate`、実行は `terraform` プロファイル（terraform-deploy IAM ユーザー）。既存リソース（S3 / CloudFront / Route53 / ACM / contact・share Lambda / SES）も import 済みで計 125 リソース（2026-11-12 時点）をコード管理。手順詳細は `Infra/terraform/README.md`
- **監視**: Route53 ヘルスチェック（`/batch/healthcheck`）+ CloudWatch アラーム（Lambda Errors ×3・投稿滞留 ×3、§7.1）→ SNS → メール通知。API は例外を捕捉して 500 を返すため Lambda Errors には計上されず、API の 5xx を直接監視するアラームは無い

### 8.2 開発環境

すべて Docker 上で動作（ルート `README.md` 参照）。**ローカル開発は移行前と同一構成**（FastAPI + MySQL を Docker Compose で起動。cron コンテナは削除済みで、バッチは手動実行）。

#### サーバー（API・バッチ Lambda） — `.github/workflows/deploy-server.yml`

## 9. セキュリティ・可用性

### 9.1 設計方針（概要書より）

- ユーザーアクセスがある部分（LP・アプリ・CSV 配信）はマネージドサービス（S3 / CloudFront）で可用性を確保。アクセス増加時も柔軟にスケール可能
- API・バッチ・データ層もフルマネージド（Lambda / DynamoDB / EventBridge）。常時稼働サーバーが無く、SSH や OS パッチ等の運用対象そのものが存在しない
- データキャッシュである CSV は S3 の自動バージョニングで保護。DynamoDB は PITR（ポイントインタイムリカバリ）有効
- Web サーバーへの改竄・ハッキングリスクは静的ホスティングにより低減
- AI によるテーマ下書き生成のみ負荷があるが、アクセス比率として極小の見込み（負荷増時は別途対応）

### 9.2 実装上の保護

| 対象 | 保護方式 |
| --- | --- |
| `/theme/generate_*` | `USER_ACCESS_KEY`（クライアント埋め込みの bot 対策キー） |
| `/theme/post_draft` | **保護なし**（アクセスキーを照合していない） |
| `/batch/*`（healthcheck 以外） | `BATCH_ACCESS_KEY`（IP 制限なし） |
| `/admin/*` | `BATCH_ACCESS_KEY` + IP 許可リスト（CIDR、`utils/security.py`） |
| 管理画面 `admin.pol-is.jp` | CloudFront Function による IP 許可リスト検査（API 側の IP 検査と二重防御） |
| 本番の Swagger | 無効化（`/docs` 等は 404。`production` と `serverless` が対象） |
| シークレット | SSM Parameter Store (SecureString)。Terraform には値を書かない（tfstate バケットは非公開・暗号化・バージョニング必須） |

### 9.3 注意事項（要改善）

- コード中のシークレット実値は 2026-07-07 に全廃した（configs の環境変数化、`services/batch.py` のフォールバック実値削除）。過去コミットに実値が残っていた pol.is ログインパスワードと `BATCH_ACCESS_KEY` は、2026-07-07 にローテーション済み（過去コミットの値は無効）。それ以外のシークレット（OpenAI・LangSmith の API キー、`USER_ACCESS_KEY`、`ENCRYPT_SALT`）は 2026-07-05 の投入時から更新していない
- `USER_ACCESS_KEY` はクライアント JS に埋め込まれるため秘匿性はない（bot 対策目的の運用であることに留意）
- `/theme/post_draft` はアクセスキーを照合していない（未対応）。登録された下書きは仕様どおり審査なしで公開されるため、**本番の `post_draft` へテスト送信してはならない**（実テーマが公開される）
- 管理画面は下書きの内容をエスケープせずに描画している（`admin.js`）。下書きは誰でも投稿できるため、スクリプト混入の余地がある
- アプリの詳細画面も、pol.is 由来のコメント本文をエスケープせずに描画している（`detail.js`）
- 既知の不具合・仕様の食い違いの一覧は `docs/画面仕様書.md` §8 を参照
